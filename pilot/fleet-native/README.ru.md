# Изолированная native-приёмка fleet5.2

Стенд проверяет настоящий WireGuard kernel, AWG2.0/3.1 userspace и OpenSSH вместе
с `FencedGateway`, `WGPeerBackend`, `SSHGateway` и production entry point агента.
Это opt-in integration test; в обычный pytest не входит.

## Запуск

Требуются Linux, Docker, `/dev/net/tun`, поддержка WireGuard в ядре, возможность
создавать контейнеры с NET_ADMIN и локальные образы:

- `family-connect-source49-tests:latest` — Python/control dependencies;
- `family-connect-amneziawg:2-pilot1` — CLI/engine AWG2;
- `family-connect-amneziawg:3.1-desktop` — CLI/engine AWG3.1.

Сборка устанавливает OpenSSH, wireguard-tools и сетевые утилиты из Debian apt.
Нужен доступ к репозиторию пакетов только при сборке. Исходные образы локальные,
теги могут меняться: точный digest итогового образа, версии инструментов и SHA256
проверенных файлов сохраняются в отчёте. Это не полностью воспроизводимая CI-сборка;
для CI потребуется отдельная фиксация базовых digest и зависимостей.

Из корня проекта:

```sh
docker build -f pilot/fleet-native/Dockerfile -t family-connect-fleet-native:accept .
python3 scripts/test_fleet_native.py --report /tmp/fc-fleet-native-report.json
```

Нельзя использовать полученный образ как рабочий gateway: в нём тестовые инструменты
и разблокированная root-учётная запись. SSH запрещает password/interactive login;
единственный разрешённый тестовый ключ имеет forced command и `restrict`.

## Изоляция

Для каждого транспорта создаются два временных контейнера с уникальными именами
`fc-fleet-native-*` и Docker network с `--internal`. Порты не публикуются,
host network/host PID/host mounts не используются. NET_ADMIN действует в сетевом
namespace контейнера, TUN передан явно. Docker создаёт/удаляет свой bridge;
VPN-маршруты хоста и рабочие сервисы не изменяются.

SSH-клиент и SSH-сервер работают в контейнере gateway через адрес11.255.255.1/32,
добавленный только на его loopback: валидатор публичных адресов не ослабляется
для теста. Это synthetic address внутри namespace, соединения с внешним владельцем
адреса нет. VPN-клиент — второй контейнер; endpoint использует внутренний Docker IP.
Следовательно, тест проверяет реальный SSH-протокол/host pin/forced command,
но не отдельный контроллер, межсерверную сеть, её задержку или внешний firewall.

Все SSH/VPN-ключи генерируются заново в контейнере; конфиги0600.
Тест передаёт client config второму контейнеру через память и stdin,
не пишет private keys в репозиторий/отчёт и не выводит stderr команд с конфигами.
`finally` удаляет оба контейнера и сеть, ошибка очистки останавливает прогон.
При принудительном убийстве самого harness очистку выполнить вручную только для
его имён, не применять глобальные prune. Тестовые образы после прогона остаются.

## Четыре сценария для каждого транспорта

1. **admit:** неверный host key и неавторизованный client key отклоняются;
   команды `id`, `fleet-v1 --initialize` и пустая модель не принимаются.
   Затем тестовый forced-command wrapper вызывает настоящий backend и завершает
   процесс через `os._exit(73)` после изменения peer, до `done=1` и receipt.
   Проверяется фактический peer и `done=0`; повтор через обычный SSH agent
   завершает pending intent, возвращает ожидаемый receipt и устанавливает `done=1`.
   Повтор готовой команды безопасен. Wrapper существует только в тестовом контейнере.
2. **restart:** VPN-интерфейс удаляется и создаётся заново с тем же серверным ключом;
   managed peer отсутствует. Локальный `--recover` восстанавливает его из журнала.
3. **remove:** удаление и его повтор успешны; запоздавший present отклоняется,
   peer отсутствует и трафик перестаёт проходить.
4. **reuse:** новая lease повторно использует клиентский ключ и адрес; повтор старого
   удаления не трогает новый peer, передача данных снова работает.

На каждом шаге сохраняется соседний unmanaged peer с адресом10.87.0.3/32.
В положительных сценариях проходят два ICMP пакета, проверяется свежий VPN handshake;
после удаления ICMP не проходит. HTTP/DNS/Internet-egress/MTU не проверяются.
После restart/reuse клиентский peer явно пересоздаётся для нового handshake:
автоматическая смена/восстановление endpoint клиентом не входит в эту приёмку.
Отчёт публикуется только после успешных12 сценариев и очистки всех ресурсов.

## Результат и дальнейшие проверки

[Checkpoint24.09](../../docs/releases/2026-09-24-fleet-native.ru.md).
Стенд закрывает локальную native-проверку WG/AWG и SSH части5.2. Он не закрывает
весь5.2: остаются единая авторизация, scheduler/signed publish, автономный TTL,
TCP backend, миграция старых выдач и production deployment/recovery service.
Полная потеря gateway и автоматическое восстановление клиента остаются этапом6.
