# Gateway credential renewal publication

This is the existing credential-only JIT path, not PROV-1 deployment or physical
rehearsal. Do not rebuild/restage runtime artifacts, change HTTP/AWG/TCP, install an
APK, create identities/admissions, reset security floors or extend the accepted TTL.

## Discover the installed contract

Read the actual bootstrap unit's `User`, `Group`, `WorkingDirectory` and `ExecStart`.
Resolve an empty `Group` through the service user's primary group. Verify the
`--family-config` path, parent/file `lstat`, ACLs and service-user open access before
changing credentials. Do not infer numeric IDs from this document.

Observed03.10.2026: `/opt/apps/family_connect/friends-restricted/gateway.json`,
`family-restricted:family-restricted`, UID/GID979, mode0600. Parent is
`root:family-restricted`, mode01770, without access ACLs. The group grants parent
traversal/write, **not credential read access**; the file remains owner-only. Sticky
directory and `fs.protected_regular` behavior are significant. No0644/0640 fallback.

## Privileged renewal versus ordinary sync

`control.friends.restricted_sync.atomic` creates a unique file as the caller using
`os.open(..., O_CREAT|O_EXCL|O_NOFOLLOW, 0600)`, writes/fsyncs, then `os.replace`.
Rename installs that new inode; it does not preserve the replaced inode's ownership.
That helper remains appropriate for ordinary sync executed as the service account.
It is **not** the root-operated gateway credential publisher.

Use `scripts.gateway_credential_publication.publish` for privileged renewal, with a
`Contract` obtained from the observed installation and a separate protected receipt
directory. The caller must serialize existing RU sync writers for this short critical
section and restore the prior timer state on all exits. The helper does not administer
systemd, issue credentials or create a second authority path.

1. Generate through the accepted issuer machinery. Validate same gateway/issuer keys,
   Family, sole owner and monotonic revisions/CRL; retain accepted lifetime policy.
2. Complete Python/native validation of the generated bytes. Pass a validator that
   returns exactly `True` only for those validated bytes; no unconditional bypass.
3. Call the publisher: unique same-directory temp → write → `fchown` → `fchmod(0600)`
   → metadata check → file fsync → actual service-identity read-open check → temp
   readback → old-inode/content guard → atomic rename → parent fsync → final
   metadata/content/read-open/readback → protected durable receipt.
4. Independently re-read the published credential and verify native validation,
   ownership/mode and service readability before restarting existing NL bootstrap.
5. Retire the old directory export and use the already committed bounded NL bootstrap
   acceptance for one reload: fresh READY directory, correct binding, stable PID,
   no unexpected restart. No journal-derived acceptance requirement.
6. Observe the certificate served by the actual control listener and compare it with
   the validated renewed certificate. Its control ALPN is **`http/1.1`**, not the
   data-session ALPN. Verify issuer signature, exact certificate, hostname and expiry;
   do not send an application request or admit another client for observation.
7. Run only the required existing sync, compare RU/NL signed CRL/floors/authority and
   directory, restore timer, and verify ordinary production unchanged.

The operator can be executed in memory through the authorized protected session;
deploying a new HTTP/sync/bootstrap runtime or staging server artifacts is unnecessary.
The live03.10 execution used the tracked publisher this way.

## Failure and replay semantics

Before rename, validation/chown/chmod/readability/write/fsync/concurrent-change/rename
failure leaves the old target untouched by this publisher and removes its own temp
where possible. It never publishes root0600 and repairs ownership afterward.

After rename, final readback, directory-fsync or receipt failures cannot honestly
promise the old inode remains installed. A durable failure receipt records
`published=true` when rename completed. If receipt writing fails, the exception says
to inspect the destination before retrying. Do not report success or blindly restore
older CRL/revision history. Persist/read back first; any authorized rollback must keep
current monotonic security state and expected ownership. An expired old certificate
is not a healthy recovery option.

Identical validated bytes with a new receipt are a verified no-op: no inode replacement.
An existing receipt is rejected rather than replayed. This is serialized operation,
not a claim of coordination with unmodified concurrent writers. No auto-renewal,
retry, credential-lifetime extension or new acceptance gate is introduced.

Receipts contain only bounded status/stage, permission metadata, booleans, timestamp
and SHA256. Credential contents, private keys, identity material and exception text
are never included. Root may administer the file; service access probes drop to the
observed non-root UID/GID with supplementary groups cleared.

## Regression coverage

`tests/test_gateway_credential_publication.py` covers publication metadata ordering,
real root/service/unrelated-user DAC in isolated temporary directories, the original
root-owned rename defect, wrong-temp-owner rejection, chmod/chown/validation/rename/
fsync failures, post-rename readback failures, receipt failures, concurrent changes,
no-op repetition and receipt secrecy. Root tests do not use production credentials.
`tests/test_gateway_publication_crypto.py` uses synthetic authority material with the
exact pinned native checker for positive and negative validation across publication.
