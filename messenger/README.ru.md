# Текстовое ядро мессенджера — прототип

Это отдельная библиотека, ещё не экран чата в Android. Она использует LXMF 1.1.1
и RNS 1.5.1; собственный новый wire-протокол здесь не создаётся.

`Chat` создаёт отдельную Reticulum identity в зашифрованном `Store`. Контакты
добавляются через `trust_contact(public)` только после внешней проверки полного
публичного ключа/отпечатка. Это явная операция доверия вызывающего приложения,
не автоматическая проверка личности человека. Сканер QR и экран проверки впереди.

`queue(address, text)` сохраняет подписанное сообщение до отправки. `attach(router)`
регистрирует отдельную LXMF delivery destination; `send(router, source, id)` передаёт
его DIRECT-методом. История сохраняет queued/sending/delivered/received. После ошибки
сообщение снова queued; после перезапуска недоставленные сообщения доступны для
явного повторного `send`. Планировщика автоматических повторов пока нет. Повтор
использует исходные подписанные байты и message ID. Дубликаты не добавляются;
устаревший callback не может изменить результат новой попытки.

`delivered` означает подтверждение LXMF-транспорта, не прочтение человеком и не
отдельное подтверждение fsync нашей базы получателя. Для такого подтверждения
понадобится дополнительный прикладной ACK. На заполненном хранилище получатель
отклоняет сохранение: нельзя показывать transport receipt как гарантию записи.

Ограничения: текст 1..4096 UTF-8 байт, не более 100 контактов/1000 сообщений.
Вложения, title/fields, команды, неизвестные отправители и неверные подписи
отклоняются. Полный Sideband interoperability пока не проверен; проверены штатный
LXMF decoder и обмен между двумя отдельными процессами через loopback RNS.

## Хранение

`Store(directory, key)` требует случайный 32-байтовый ключ от приложения.
**Не сохранять ключ рядом с базой.** Поддержка Android Keystore/системного keyring,
восстановление ключа и пользовательские резервные копии ещё не реализованы.
Потеря ключа означает потерю доступа к истории и chat identity.

Каталог — отдельный 0700, база/lock — 0600, один процесс-владелец. Использовать
доверенный родительский каталог без изменяемых посторонними пользователями путей.
Все значения записей, включая identity/контакты/текст/статусы, шифруются AES-256-GCM;
record ID связан с ciphertext через AAD, подмена строк обнаруживается. SQLite
журнал содержит ciphertext. Видны число/размер записей и message IDs. Защиты от
удаления записей/отката всей базы или компрометации работающего процесса нет.

RNS/LXMF runtime/ratchet state требует собственного приватного каталога. Store
не шифрует файлы стороннего router. Включать propagation mode нельзя без отдельной
приёмки. Перед закрытием Store вызывающая программа должна остановить router и
дождаться callback. У этого прототипа пока нет полного service lifecycle.

## Проверка без APK и сервера

В отдельном virtualenv установить `control/requirements.lock` и
`provisioning/requirements.lock`, затем:

```sh
python -m pip install --no-deps --require-hashes -r messenger/requirements.lock
python -m pytest -q messenger/tests
```

Тесты создают только синтетические identities в pytest tmpdir. Сетевой тест
использует TCP на 127.0.0.1 и два дочерних процесса, удаляет процессы в finally.
Рабочие VPN-профили, relay и пользовательские переписки не используются.

## Offline-доставка (локально проверенный прототип)

`send(router, source, id, via_relay=True)` явно выбирает PROPAGATED-доставку.
До вызова приложение должно настроить доверенный node address через
`router.set_outbound_propagation_node(...)`. Статус `relayed` означает только
приём узлом; он не превращается в `delivered` после скачивания адресатом.
Прикладное подтверждение сохранения отправителю ещё предстоит реализовать.

Для получения использовать `Mailbox(chat, source, trusted_node_public).sync()`
из `messenger.mailbox`, а не штатный `request_messages_from_propagation_node()`:
путь Family Connect сначала расшифровывает сообщение, проверяет контакт/подпись
и сохраняет в Store, затем отправляет запрос удаления. Ошибка записи оставляет
сообщение на узле. Повтор уже сохранённого сообщения безопасен. Параметр
`delete_after_store=False` оставляет копию на узле для повторного получения.

Sync создаёт свежий link, идентифицируется chat identity, использует доверенный
публичный ключ узла и закрывает link в finally. После отказа доступа можно повторить
запрос без перезапуска приложения. По умолчанию сетевой бюджет12s (максимум30s),
до10 сообщений/48KB в запросе, максимум70KB response и1000 IDs в списке. Файловый
fsync не имеет жёсткой real-time гарантии. `cancel` — threading.Event. Параллельный
sync одного Mailbox отклоняется. Планировщика автоматической синхронизации пока нет.

Стенд проверяет перезапуски узла/получателя, ошибку записи, повторное скачивание,
запрет скачивания для identity вне allowlist, удаление после сохранения, upstream
очистку по объёму/сроку. Узел слушает только127.0.0.1, использует синтетические ключи.
Ключи рядом с базой в test fixture — исключительно для воспроизводимого перезапуска,
не пример хранения ключей приложения. Реальный PoW проверяется с одним worker.

До размещения узла в Amsterdam остаются ограничения: LXMF allowlist защищает
скачивание, анонимный приём с валидным PoW остаётся возможным; ограничение объёма
применяется cleaner-ом после приёма и не является жёсткой дисковой квотой. Нужны
ограничение входящего приёма, отдельная служба/пользователь, дисковый лимит и lifecycle.
Срок30 дней проверен искусственным старением синтетических записей, не ожиданием
30 дней. На узле видны адрес получателя, объём и время ciphertext. Не считать
этот стенд развёрнутым или готовым к публичному использованию сервером.

## Закрытый Family Connect ingress

Добавлены `ClosedRelay`/`Spool` и `Mailbox.publish(id)`: криптографически
идентифицированный отправитель, закрытый список адресатов, pre-insert quotas,
rate limit и подтверждение после FULL commit. Publish сохраняет encrypted envelope
в локальном Store, поэтому повтор после потери ACK/перезапуска не расходует квоту
узла повторно. Содержание по-прежнему LXMF, но ingress — отдельный прикладной
request path: обычный PROPAGATED sender не следует переключать на этот узел.
GET совместим с нашим Mailbox. Установленное Android-приложение не менялось.

[Пределы хранилища/реальный ENOSPC и условия серверного пилота](../pilot/messenger/README.ru.md).
Ограничения anonymous upload и cleaner-only quota из предыдущего раздела относятся
к штатному LXMF propagation node; новый закрытый endpoint устраняет их на уровне
приёма/базы. Постоянный ограниченный runtime том и служба ещё не развёрнуты.

## Компактность и живой сервер

Компактный бинарный обмен — обязательный принцип. Живой Amsterdam-пилот проверил
отложенную доставку и перезапуск:4 байта текста →115 байт LXMF →208 байт ciphertext.
Служебный обмен измеряется отдельно; следующий шаг — бюджет трафика серии/idle.
[Результаты и границы](../docs/releases/2026-09-13-amsterdam-mailbox.ru.md).
