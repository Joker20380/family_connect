# Fleet: шлюзовой журнал операций и рабочий цикл

Локальный прототип от24.09.2026. Код: [gateway](../control/fleet_gateway.py),
[worker](../control/fleet_worker.py), [проверки](../tests/test_fleet_gateway.py).
Основа: [центральные leases](fleet-leases.ru.md).

## Зачем нужен второй журнал

Запись generation только в управляющей базе не останавливает старую команду,
которая уже отправлена на сервер. Например: создание задержалось → контроллер
запросил удаление → адрес переиспользован → запоздалое создание вернуло старый peer.
Поэтому сам gateway должен помнить отмену и сериализовать фактические изменения.

FencedGateway сохраняет intent в своей SQLite-базе **до** вызова backend.ensure.
Удаление generation2 сохраняет постоянный запрет на создание generation1 того же
lease ID. После успешного удаления запись остаётся tombstone, а не удаляется из DB.

## Формат и доверие

PeerCommand содержит lease ID, gateway ID, device reference, public WG key,
внутренний IPv4 `/32`, transport/version, expires_at, generation и operation.
Поддержаны команды WG1, AWG2.0/3.1; это не подтверждение поддержки managed AWG3.1
клиентскими verifier. TCP-команды пока отвергаются, worker оставляет их pending.

Lifecycle намеренно ограничен существующими неизменяемыми leases:
present/generation1 → absent/generation2. Продление той же записи, смена ключа,
адреса или срока в ней не разрешены. Новый lease имеет новый ID.
Проверяются gateway binding, совместимость транспорта и принадлежность адреса
операторскому пулу; сеть, gateway address и broadcast не разрешены.

Gateway-конфигурация закрепляется при явной инициализации отдельного каталога0700
и DB0600. Другой gateway config не может использовать старый журнал. Файл нельзя
подменить symlink; потерянная DB не создаётся при обычном execute/recover.
Текущие ограничения backup/rollback такие же, как для центрального store: возврат
старой копии журнала разрушает fence и не является допустимым штатным откатом.

Это внутренний API доверенного управления. Сетевой listener, аутентификация SSH/mTLS
и загрузка секретов в прототип не добавлены. Receipt содержит точные lease/gateway/
generation/operation и SHA256 canonical command; он не подписан и имеет смысл
только на доверенном, аутентифицированном пути adapter. Клиентский ACK не является
таким receipt. Bool в integer-полях отвергается до сериализации/побочных эффектов.

## Что происходит при execute

1. Проверяются команда, gateway config и monotonic clock; берутся локальные locks.
2. Сохранённый binding lease обязан совпадать. Команды меньшей generation запрещены.
3. Точный завершённый повтор возвращает прежний receipt без нового изменения peer.
4. Новый present резервирует адрес и public key уникальными индексами журнала.
   Pending removal продолжает держать оба ресурса.
5. Fence/intent commit выполняется до backend.ensure. Backend должен синхронно и
   идемпотентно добиться требуемого состояния либо сообщить об ошибке.
6. Только после успеха done сохраняется; для absent освобождаются held resources.
   Receipt возвращается после этого commit.

Если absent пришёл раньше самого первого present, достаточно сохранить tombstone
без обращения к backend: этот журнал ещё не разрешал установку данного lease.
Это не позволяет неизвестному lease удалить чужой peer с совпадающим ключом.
Предполагается, что **все** управляемые установки проходят через этот журнал.

Повтор завершённого absent никогда снова не вызывает backend.remove/ensure. Иначе
он мог бы удалить более новый lease, уже использующий тот же WG key или IP.
После сбоя между эффектом и done повторяется только pending intent, удерживающий
ресурсы; новый lease их ещё получить не может.

## Дочерние процессы и падение родителя

Во время эффектов удерживается дополнительный `.effects.lock`. Backend получает
его FD и обязан передать его каждому дочернему процессу, способному ещё выполнить
изменение, через `pass_fds` либо эквивалентное наследование. Потомки также должны
сохранять FD до завершения всех эффектов. Нельзя запускать detached работу, которая
теряет FD, но позже снова изменяет интерфейс.

Родитель закрывает свой FD без явного LOCK_UN: open file description может ещё
принадлежать дочернему процессу. После смерти родителя новый обработчик не начнёт
удаление до завершения старого дочернего эффекта. Длительность и отмена внешних
процессов должны быть ограничены конкретным backend; зависший потомок удерживает
lock и приводит к недоступности операций, а не к обходу защиты.

В тесте реальный subprocess запускает дочерний отложенный эффект и завершается
`os._exit(23)`. Конкурирующее удаление ждёт освобождения дочернего FD и выполняется
последним. Это доказательство механизма для соответствующего fixture backend,
не автоматическая гарантия для ещё не написанного WG/AWG/TCP adapter.

## Recovery и worker

Gateway recover сначала завершает pending removals, затем восстанавливает desired
present peers, в том числе после потери volatile-конфигурации VPN engine.
Завершённые absent tombstones не исполняются повторно. Истёкшая установка не
восстанавливается: нужна команда удаления от контроллера. Автономный gateway TTL
sweeper пока не реализован. До успешного восстановления и реального health probe
узел нельзя объявлять готовым для новых назначений.

FleetWorker.once выполняет конечный проход:

- Центральный store переводит expired leases в retiring.
- Worker получает pending и перепроверяет work_item/binding/generation.
- Adapter выбран из операторского mapping по gateway ID; адрес клиента не может
  превратиться в произвольную SSH-команду.
- После точного receipt central store повторно проверяет состояние и выполняет
  mark_ready либо confirm_removed.
- Ошибка сети/ответа/adapter оставляет pending; гонка с retire/revoke не возвращает
  lease в ready. Диагностика содержит фиксированные retry/state-changed outcomes,
  а не exception text с возможными credentials.

Gateway effects не выполняются под SQLite-транзакцией центрального store. Отзыв
может пройти одновременно с установкой: тогда central mark_ready будет отвергнут,
а последующий проход удалит peer через generation2. Потерянный receipt повторяется
без повторного завершённого эффекта. Durable scheduler/backoff/fairness, сеть,
конкретный peer backend и transactional signed publication ещё не подключены.

## Связь с Django-админкой

Согласован [пункт7.1](PLAN.md#django-admin): серверы, устройства/доступ,
подписки/платежи и журнал операций в одной Django-панели. Её действия должны
создавать durable intent через общие сервисные методы. HTTP worker Django не
выполняет WG/SSH, не стирает tombstones и не меняет leases прямым редактированием.
Повторная кнопка/платёжное событие использует idempotency key. Доступ меняется
через entitlement/revoke; платёжный webhook не командует сетевым интерфейсом.

## Граница текущего шага

Прототип проверен локально с изолированными моделями peer state и настоящими
дочерними процессами. Рабочие gateway services, DB и клиентские версии не менялись.
Следующий шаг: реальный bounded backend с сохранением посторонних peers,
аутентифицированный adapter, TTL/restart policy, интеграция с авторизацией Friends,
затем signed publication. Native/live fault-тесты остаются обязательными.

## Последующее продолжение: durable scheduler

[Checkpoint access/scheduler](fleet-access-scheduler.ru.md) добавил persistent claims
и backoff в центральную fleet DB схемы2. Gateway journal остаётся схемы1.
Для supervised обработки используется FleetScheduler; FleetWorker.once — прежний
диагностический проход без сохранения задержек. Remote fencing по-прежнему обязателен.
