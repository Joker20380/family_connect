# Мессенджер Family Connect поверх Reticulum: план и прототип — 13.09.2026

Реализовать можно. Предлагаемый транспорт сообщений — [LXMF](https://github.com/markqvist/LXMF)
поверх Reticulum. LXMF уже предоставляет end-to-end encryption, очереди и
подтверждения доставки; propagation nodes хранят зашифрованные сообщения для
недоступных получателей. Реальный совместимый клиент — [Sideband](https://github.com/markqvist/Sideband).
На 13.09 реализовано отдельное текстовое ядро: encrypted Store, отдельная identity,
контакты, durable outbox и DIRECT-обмен двух синтетических пользователей.
[Код и ограничения](../messenger/README.ru.md), [приёмка](releases/2026-09-13-transports-messenger.ru.md).
Android UI и сервер offline-доставки пока не реализованы.

Первый продуктовый объём: личный текстовый чат, контакты по адресу/QR с проверкой
отпечатка, статусы «в очереди / отправлено / доставлено / ошибка», история и повторная
отправка после восстановления сети. «Доставлено» не означает «прочитано».
Группы, звонки, большие вложения и синхронизацию нескольких устройств отложить.

## Интеграция

- Использовать UX регистрации устройства, но отдельную chat identity и отдельные
  destination/state. Не превращать VPN identity/operator key в ключ переписки.
  Связь контакта с зарегистрированным устройством должна быть явной и проверяемой.
- Общий RNS процесс/соединение возможен после проектирования broker lifecycle.
  Текущий managed control route — ограниченная lease для обмена конфигурацией;
  он не является готовым постоянным транспортом чата. Нужен отдельный жизненный
  цикл с учётом VPN, сна, смены сети и закрытия приложения.
- Разделить VPN journal/ACK и inbox/outbox мессенджера. Текст чата никогда не
  интерпретируется как команда смены VPN; VPN configuration не становится сообщением.
- Локальная история требует собственного защищённого хранилища и удаления данных.
  Шифрование транспорта LXMF само по себе не шифрует SQLite/history на диске.
- Amsterdam RNS relay — основа связности. Он пока не LXMF propagation node.
  Для offline доставки нужна отдельная служба, пользователь ОС, каталог, квоты,
  retention и ограниченный круг пилотных identities. Новые зависимости закрепить
  и проверить совместимость с установленным RNS1.5.1 до развёртывания.

## Этапы и приёмка

1. Локальные два синтетических пользователя: двусторонний текст, проверка подписи,
   подтверждение доставки, дубликаты и перезапуск. Проверить совместимость с Sideband.
2. Изолированный propagation node: получатель offline, отправка, восстановление,
   получение без дублей; проверка квот/retention и отсутствия plaintext на узле.
3. Linux preview: контакты/история/очередь, защищённые ключи и история, маршруты
   с VPN on/off, crash/suspend/reconnect. Native Windows/Android — отдельная приёмка.
4. Малый закрытый Amsterdam pilot с измерением ресурсов рядом с VPN/relay;
   размер сервера выбирать по CPU/RAM/диску/объёму очередей, а не по обещанию ёмкости.

Reticulum не создаёт отсутствующий физический канал. Пока есть только TCP/IP relay,
при полной потере этой связности сообщения ожидают восстановления. Работа через
локальную сеть/радио требует доступного поддерживаемого интерфейса и оборудования.
Один Amsterdam VPS также не даёт независимого резервного пути.

Статус: этап 1 частично принят — отдельные процессы, подписи, доставка,
дедупликация и восстановление локальной очереди проверены. LXMF 1.1.1 установлен
только в изолированной среде /tmp; рабочая RNS-служба не изменена. Sideband,
автоматические повторы после потери сети и полный lifecycle остаются открытыми.
Этап2 локально проверен: offline-получатель, перезапуск узла, ciphertext spool,
повторное получение без дублей, ошибка записи без purge и очистка по лимиту/сроку.
[Приёмка и ограничения](releases/2026-09-13-messenger-offline.ru.md).
Закрытый прикладной ingress и pre-insert квоты реализованы; hard SQLite limit и
реальный ENOSPC отдельного тестового тома проверены. [Отчёт](releases/2026-09-13-closed-mailbox.ru.md).
До серверного пилота: постоянный ограниченный том под RNS/cache/spool и служба с
ограничением памяти, отдельной identity и проверенным bootstrap.
Затем Android Keystore/чат; автоматической синхронизации и прикладного ACK пока нет.
Приоритет клиента — Android; Linux остаётся стендом для transport/backend проверок.
Новые APK по текущему решению пользователя не упаковываем.
