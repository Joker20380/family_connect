# Initial Docker generation transition — NOT AUTHORIZED / NOT QUALIFIED

28 November source follow-up adds an executable negative retirement scenario (`--retire-control-processes`)
to the isolated exact-Engine harness. It kills and reaps dockerd/containerd while pre-hook create/start
handlers are held, then tests an already detached shim-owned writer through its open FD, shared mmap
and rename, and recovers only the disposable Engine. Until its independent result is accepted, it
is a candidate, not proof. Even successful lab API recovery is not console/support recovery, and
does not establish new-controller cleanup or a production window.

Finite architecture decision: do not promote either online hook attachment or control-process
retirement to initial coverage. If the old generation cannot be placed under one independently
held physical ancestor with all dispatches covered, require a cold kernel-generation transition
under a boot-time Docker admission interlock; a different dockerd PID is insufficient. That fallback
has host-wide impact beyond the14 containers and itself needs disposable-VM qualification (including
boot-time prevention of legacy automatic restart, durable failed phases and new-controller recovery)
before any production scope request. No host reboot, interlock installation or shared stop is authorized
or executed here. This is the finite fallback, not another census-based proposed proof.

The27 November isolated stock Engine29.1.3 pre-hook test deliberately blocks Create/Mount
inside a disposable volume driver, after the actual Engine handler accepted the request.
No HTTP proxy or AuthZ hook delays these initial requests. Containers use protected Binds,
empty CgroupParent and unless-stopped, matching the installed pair's relevant configuration.
After the first AuthZ attachment, a new direct protected create gets403, but releasing the
old callbacks produces create201 and start204 plus a real file write outside the new parent.
Thus online attachment alone cannot set initial_admission_coverage_proven=true.
This is a counterexample, not a qualified shared-daemon transition or evidence about every
possible Engine transition design. The controlled volume driver is disposable fault injection,
not a claim that production uses that driver. Existing FD/mmap/restart component proofs do not
repair this initial gap. No production daemon, container or policy was modified.

## Candidate one-time window, still requiring isolated qualification

1. Before admission close: accept current panel/support/IPC/MESH baseline; load the existing HA
   key in memory, export effective compose/configuration (never seed_demo), retain exact images,
   mount identities, restart policies and unit/drop-in hashes. Obtain explicit cross-application
   maintenance ownership and bounded normal-recovery contracts for all17 running containers.
   A code-only rollback must not restore old product bytes. Establish a maximum agreed downtime;
   no production duration is currently qualified and no window has been scheduled.
2. Close authenticated project gates and all known launch paths; additionally block shared Docker
   socket activation/API admission and supervisor restart launches for the approved window.
   Stop specific applications normally, including whole writer trees; stopping the main PID is
   insufficient. Keep durable intent and exact failure receipts. Never replay unknown operations.
3. Retire the old dockerd handlers **and** their containerd/shim/runc task generation. This needs
   independently held, empty/frozen physical execution domains covering all old dispatches,
   including in-flight create with as-yet-unreported ID, old namespaces/FD/mmap/renames and restart
   policy. Process absence or task enumeration alone cannot substitute for that boundary.
   Stock shared generation retirement with these guarantees remains the specific unqualified step.
4. Only after that proof, start a new daemon generation with mandatory resource-scoped AuthZ.
   Recreate only console/publisher from their exact installed images/effective configuration with
   dedicated CgroupParent/restart=no. Preserve all volumes and the support runtime-directory mount;
   the required runtime directory must exist with its accepted ownership before console creation.
   PostgreSQL/neighbor configuration must remain unchanged; their restart after an approved shared
   outage is separate from a project recreation. New-generation checks must prove old dispatches
   cannot execute, not merely that new requests get403.
5. Verify cleanup/recovery with a replacement controller using immutable transition phases and
   physical generation identity; it must not inherit a dead controller's capture lease. Lost
   stop/release responses require read-only reconciliation, not blind replay. Resume only own
   restrictions, restore application-specific dependencies, login/pages/IPC/timers and both-NL
   DNS/HTTPS/egress. Failure to prove any old domain empty means NO_CAPTURE, retained fencing and
   bounded recovery under the separately approved shared-window procedure.

Qualification still required: controller/enforcer loss, already-open FD/prefaulted mmap, old exec
descendants, pending runtime handoff, internal restart, partial cleanup and lost response, using the
same physical generation fence, plus exact-image application recovery. No experiment on neighboring
applications is permitted. No INSTALL or maintenance acceptance follows from the counterexample.
Until this step and the remaining OWNER/support/remote composition are qualified, no common kit.
