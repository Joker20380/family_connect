# Windows TCP: подписанный профиль и защищённое хранение

TCP-движок прошёл отдельную Windows-приёмку. Теперь broker поддерживает
`activate-tcp`: принимает подписанный профиль, проверяет привязку к ключу устройства
и сохраняет его через DPAPI LocalSystem в закрытом ProgramData/FamilyConnect.
Профиль выбирается по SID клиента named pipe; клиент не задаёт путь или владельца.
Статус возвращает только наличие TCP-профиля (`tcpReady`), без реквизитов доступа.
Команда `connect` пока запускает существующий WG; TCP import ещё не выведен в GUI.

## Выдача оператором

Использовать существующий ключ активации, соответствующий установленному
`clients/windows/activation.pub`. Не создавать новый ключ и не использовать ключ
подписи обновлений вместо ключа активации. Закрытый ключ остаётся у оператора.

На Windows получить существующий код устройства FC1. Подготовить отдельный
TCP-профиль `vless-reality-v1` для этого устройства и зарегистрировать его на gateway
по действующему runbook. Данный скрипт не создаёт пользователя на сервере.
Нельзя выдавать один UUID нескольким устройствам.

```sh
python -m scripts.activate_windows_tcp \
  --key /private/path/activation.key \
  --profile /private/path/device-tcp.json \
  --request FC1-DEVICE_PUBLIC_KEY_HEX \
  --sequence 1 \
  --output /private/path/device.fctcpactivation
```

Результат содержит TCP credential, поэтому передаётся устройству приватно и не
попадает в Git, CI, issue, чат или публичный release. Новый файл создаётся без
перезаписи; на Unix umask 077. На Windows оператор обеспечивает закрытый каталог.
В штатном приложении кнопка импорта появится вместе с жизненным циклом TCP;
пока импорт доступен только через broker API для интеграции.

## Проверки и срок действия

Ed25519 domain: `family-connect/windows-tcp-activation/v1\0`.
Допустимы только известные поля, canonical IPv4 endpoint, UUID, REALITY public key,
DNS server name для SNI и short id. Loopback/multicast/нулевые идентификаторы,
лишние или повторяющиеся JSON-поля и executable hooks отвергаются.
Подписанный профиль не является произвольной конфигурацией Xray: фиксированный
TUN/VLESS/REALITY JSON создаёт сам клиент; DNS/маршруты здесь ещё не применяются.

Срок импорта — 24 часа, верхний предел принимаемого срока — 7 дней.
После успешного импорта профиль сохраняет работоспособность офлайн; это не механизм
отзыва подписки. Отзыв выполняется сервером. Повторная проверка подписи сохранённого
профиля происходит при чтении; ключ доверия не берётся из импортированного файла.

`sequence` увеличивается для данного устройства. Меньшая версия отвергается;
та же версия допустима только для того же проверенного содержимого. Новая версия
заменяет профиль атомарно; подпись и sequence хранятся вместе в одном DPAPI-файле.
Неверный/чужой/просроченный профиль не меняет предыдущий файл.

## Следующий шаг и приёмка

Остались запуск/остановка Xray службой с владением процессом, crash cleanup,
маршруты IPv4/IPv6 и DNS, GUI и восстановление соединения, затем Windows AWG.
После завершения Windows — транспорты Android; затем этап 5 Reticulum:
доставка подписанных настроек, проверка, применение с ACK и откатом.
Для этапа 6 (смена заблокированного gateway) потребуется независимый второй VPS.
Разработка Reticulum не зависит от появления кнопки обновления Android или Google Play.

Windows CI проверяет реальную установленную службу и LocalSystem DPAPI на
синтетической активации: временный тестовый anchor восстанавливается в finally,
тестовый TCP-профиль удаляется. Тест запускается только на disposable elevated
Windows CI runner. Производственные профили и ключи не используются.
