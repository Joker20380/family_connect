# Две серверные площадки

[English](distributed.en.md) · [Главная](../README.ru.md)

**Статус: межсерверное развёртывание демонтировано по решению владельца.** На `186.246.51.201` удалены код, ключи, контейнеры, сети, образы и установочные архивы Family Connect. Сервер оставлен для сайтов; повторно использовать его для VPN без нового прямого указания владельца нельзя. На первом сервере удалён межсерверный туннель, каталог обновлён до epoch 3 с gateway-lab, relay-a и relay-b. Ниже сохранена история испытания, а не текущая конфигурация.

## Развёрнутая схема

- `185.251.89.19`: control plane, управляемый российский gateway, резервный relay-a.
- `186.246.51.201`: relay-remote в `/opt/apps/family_connect-relay`.
- Оба внешних IP при проверке определялись как RU. Географическое резервирование не доказано.

```text
тестовый Linux-клиент на первой VPS
  → служебный WireGuard между VPS → relay-remote на второй VPS
  → служебный WireGuard обратно → российский gateway → интернет

отказ удалённого relay и служебного маршрутизатора:
  клиент → локальный relay-a → тот же gateway → интернет
```

Это реальный межсерверный трафик, но ещё не клиент на телефоне/ноутбуке в Европе.
Пользовательский прямой WireGuard на UDP/51820 продолжает работать отдельно.

## Identity, маршруты и Reticulum

Приватный identity-ключ удалённого relay создан на второй VPS и её не покидает. Первый сервер
получил публичный CSR, выдал сертификат и включил identity/отпечаток в подписанный каталог.
Адрес relay в каталоге — `172.29.94.11:4444`; gateway — `172.29.93.10:4433`.
Удалённый relay обновляет подписанный каталог через служебную сеть и хранит проверенный кэш.

Сам Reticulum не установлен. Identity отделена от адреса, но транспорт использует IP.
В этом этапе публичные endpoints служебного WireGuard фиксированы в операторской конфигурации.
Автоматическое обнаружение нового публичного IP, исчезновение gateway и распределённый
bootstrap без доступного первого сервера ещё не реализованы. При полном отказе control plane
действительный кэш разрешает работу только до истечения подписанной аренды, обычно 15 минут.

## Изоляция

- Compose-проект второго сервера: `family-connect-remote`; существующие приложения не менялись.
- Проект первого служебного маршрутизатора: `family-connect-site` в `/opt/apps/family_connect-site`.
- UDP/51830 публикуется только для служебного WireGuard. UDP relay/gateway не открыт напрямую.
- Relay работает без capabilities в отдельной внутренней Docker-сети. Служебный маршрутизатор
  пересылает только клиентские UDP-пакеты к relay, UDP к gateway и TCP к control API.
  Произвольный публичный egress через него запрещён firewall.
- Интернет-выход остаётся только на первом управляемом gateway; второй сервер не становится exit.
- Служебные ключи создаются отдельно на каждой VPS; между ними передаются только публичные ключи.
  Runtime-каталоги `state-site/`, `state-remote/`, `state-enroll/` исключены из Git/build context.
- Контейнер `routes` подготавливает сетевое пространство до запуска relay. Проверка готовности
  подтверждает маршрут, а не требует постоянного ответа API. При пересоздании `routes` нужно
  пересоздать и `relay`, поскольку они используют общее сетевое пространство.

Служебный WireGuard использует MTU 1440 для проверенного IPv4-пути между этими серверами,
чтобы вместить внешний QUIC с UDP payload до 1400 байт. Произвольные мобильные MTU не проверены.

## Эксплуатация

На первой VPS уже подготовлен `family-connect-data` и его сеть `172.29.93.0/24`.
Служебный маршрутизатор подключается к ней как `172.29.93.254`; удалённая сеть — `172.29.94.0/24`.
Каталог теперь предпочитает relay-remote и содержит relay-a как резерв. Прежний relay-b остановлен.

```sh
# Первая VPS, /opt/apps/family_connect-site
docker compose -f compose.site-primary.yaml up -d

# Вторая VPS, /opt/apps/family_connect-relay
docker compose -f compose.site-remote.yaml up -d

# При пересоздании сетевого пространства на второй VPS
docker compose -f compose.site-remote.yaml up -d --force-recreate routes relay
```

Ключ маршрутизатора монтируется для UID 0; identity/cache relay принадлежат UID 65532.
Каталоги ключей имеют режим 0700, приватные файлы — 0600. Публичный trust доступен для чтения.
`site_key.py` создаёт ключ локально; `identity.py` создаёт локальный ключ и CSR;
`register_relay.py` выполняет операторскую выдачу сертификата и атомарное обновление каталога
с увеличением epoch под общим lock. Команда не является публичным API регистрации.
Нельзя копировать CA private key или приватный ключ relay между VPS.

Для повторения испытания **с операторского ноутбука**, где уже есть SSH-доступ к обеим VPS:

```sh
python3 scripts/test_distributed.py
```

Тест создаёт временный клиент на первой VPS, проверяет прирост байт служебного туннеля второй,
начинает одну HTTPS-загрузку без retry/resume и останавливает только два контейнера Family Connect
на второй VPS. Остальные приложения и сам сервер продолжают работать. Затем удалённый контур
восстанавливается, тестовый клиент удаляется. SSH-ключи оператора остаются на ноутбуке.

Старый `test_data.py` предназначен для односерверного каталога. При активном relay-remote он
отказывается разрушать эту топологию. Нельзя откатывать подписанный каталог к меньшему epoch.

## Результат и границы

[Отчёт испытания](distributed-validation-result.json) фиксирует 8 MiB, одно HTTPS-соединение,
одну внутреннюю QUIC-сессию и одно переключение после остановки удалённого контура.
Ограничение curl — 256 KiB/s; это функциональная проверка, а не измерение пропускной способности.
SHA-256 наблюдаемая; TLS защищает целостность публичной HTTPS-передачи.

Испытан отказ сервисов на второй VPS, не отключение питания и не потеря первого сервера.
Gateway/control всё ещё на первой VPS, а тестовый клиент также находился на ней. Сохранение
сессий при смене gateway, независимые географические маршруты, публичный IP mobility и работа
Android через адаптивный контур остаются следующими этапами.

Сертификат relay выдаётся на 30 дней; автоматическое продление пока не реализовано.
