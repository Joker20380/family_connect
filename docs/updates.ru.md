# Обновления клиентов

## Как работает первый вариант

Начиная с 0.2.1 Linux и Windows имеют кнопку «Проверить обновления». Проверка выполняется
только по нажатию. Клиент получает `updates/pilot.json` по HTTPS из основного репозитория,
проверяет Ed25519-подпись по встроенному `update.pub`, срок и монотонный sequence.
Старые/подменённые каталоги отвергаются; уже установленная либо более старая версия
не предлагается. После подтверждения пользователя скачивается соответствующий файл,
проверяются размер и SHA-256 из подписанного каталога. Неподписанный release.json на
странице GitHub информационный и не является разрешением обновления.

Linux сохраняет код в `~/.local/share/family-connect/releases/`, выполняет smoke-проверку
и атомарно переключает `current`, сохраняя `previous`. Ярлык использует current/app.py.
Данные обновлений/floors отдельно: `~/.local/state/family-connect-updates`. Профили
NetworkManager не переносятся и не удаляются. Начиная с 0.2.7 нужны GTK 4/libadwaita, Python GI и
`python3-cryptography`: `sudo apt install python3-gi gir1.2-gtk-4.0 gir1.2-adw-1 python3-cryptography`.
На текущем ноутбуке зависимости уже установлены. На других Linux сначала установить
зависимости; неуспешная smoke-проверка сохраняет старую версию. Первую установку старого клиента
0.1/0.2 без обновлятора выполняет install-linux.sh; последующие — кнопка приложения.

Windows хранит состояние проверки в `%LOCALAPPDATA%/FamilyConnect/updates`, скачивает
установщик, повторно проверяет хеш перед запуском и вызывает стандартный UAC.
Установщик обновляет приложение поверх прежнего с сохранением `%ProgramData%/FamilyConnect`
и DPAPI-ключей. Служба перезапускается, VPN может кратко прерваться — это указано перед
подтверждением. Подпись каталога не заменяет Authenticode установщика: текущий pilot
по-прежнему без сертификата издателя, официальный драйвер сохраняет свою подпись.

## Роль Reticulum

Подписанный каталог не зависит от HTTPS. `Updater.accept(raw)` в Linux и
`Updates.Verify(raw, anchor, now)` в Windows принимают те же байты от любого транспорта.
Следующий шаг — RNS notification/catalog provider. Самого работающего RNS listener в
приложениях 0.2.1 нет; уведомления пока не отправляются через Reticulum. Большие пакеты
передаются по HTTPS. Ни доверие к RNS-узлу, ни ссылка в уведомлении не заменяют подпись.

## Выпуск оператором

Приватный Ed25519-ключ: **только локально** в
`state-client-build/update-signing/ed25519.key` (0600, каталог 0700, исключён из Git).
Резервную копию хранить отдельно офлайн; не передавать ключ в CI, сервер или чат.
В репозитории находятся только публичные anchors и воспроизводимый тестовый ключ fixture,
не совпадающий с реальным anchor. Повторно генерировать production-ключ нельзя: старые
клиенты перестанут доверять обновлениям. Ротация требует отдельного подписанного перехода.

1. Повысить VERSION и версии Linux/Windows/installer. Никогда не менять уже выпущенный
   tag или подменять файлы под тем же version.
2. Commit с префиксом `Release ` в main запускает CI. Release job публикует pilot только
   после успешных Windows и Linux jobs. Либо использовать новый `vX.Y.Z` tag.
3. Скачать ровно опубликованные архив/EXE. Проверить результаты CI и SHA256SUMS.
4. Подписать каталог, повысив sequence относительно последнего опубликованного:

```sh
python scripts/sign_update.py --key state-client-build/update-signing/ed25519.key --version 0.2.1 --sequence 1 --artifacts artifacts/clients/0.2.1 --output updates/pilot.json
```

5. Проверить каталог обоими verifier и закоммитить updates/pilot.json. Приватный ключ
   не участвует в GitHub Actions. Срок каталога — 90 дней; продление тоже повышает sequence.
6. Старая версия с обновлятором обнаружит новый выпуск по кнопке. Для устройств до 0.2.1
   требуется один ручной переход. Обновление приложения и migration сервера независимы.

Если скачивание, подпись, размер, хеш или smoke не проходят, обновление не применяется.
Linux previous остаётся для ручного возврата к прежнему коду; не сбрасывать floors ради
принятия неподписанного/старого каталога. Полное восстановление старого backup владельцем
ОС не блокируется аппаратно. Автоматическое применение без пользователя, стабильный
канал, подписанный recovery/root rotation и Android update flow ещё впереди.


### Обновление и активация

В приложении: «Проверить обновления» → «Установить обновление» → подтверждение.
Ручная пересылка установщика не требуется. Каталог GitHub может кратковременно
отдавать предыдущую версию из кеша; повторите проверку позже.

Обновление сохраняет ключ и активацию. Файл `.fcactivation` нужен отдельно, если
после переустановки требуется восстановить активацию; при каждом обновлении получать
его заново не нужно. Для восстановления оператор сверяет текущий код устройства.
