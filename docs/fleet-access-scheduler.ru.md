## Авторизация выдачи

`FleetAccess` использует ту же таблицу `access`, что резервирование, worker и
проверка publishable. Второго хранилища прав внутри fleet нет. Устройство не может
само создать grant или передать max_leases/expiry доступа. `set_access` — доверенный
внутренний API будущего сервиса доступа/админки, а не публичный endpoint.
Действующая Friends DB пока не подключена: импорт и переключение единственного
источника прав требуют отдельного этапа, периодическая двусторонняя синхронизация
двух независимых источников прав не предусмотрена.

Публичный контракт будущего входного обработчика:

1. `challenge(public=..., wg=..., request=...)` принимает public RNS identity,
   WG key и строго проверенный `Reservation`: request_id, registry_revision,
   country, transport, version, lifetime и address_families. Поддержаны WG1,
   AWG2.0/3.1; TCP через этот путь пока запрещён. Метрики/endpoint, устройство
   получателя, права, цены и лимиты не принимаются из пользовательского request.
2. Проверяется существующий grant, неизменность public binding, revoke/expiry.
   В базе сохраняются hash случайного nonce, device, revision доступа, точный
   request и срок до120с, ограниченный expiry доступа. Одновременно допускается
   до8 действующих challenges на устройство; истёкшие записи очищаются при запросе.
3. Ответ содержит challenge, expires_at, audience и echo принятого request.
   Клиент должен сравнить echo со своим запросом и подписать challenge только
   через доверенный служебный канал. Audience — `family-connect/fleet-reservation/v1`.
   Подпись enrollment/Friends с другим audience здесь не принимается.
4. `complete(proof, observations=...)` проверяет подпись существующим механизмом
   DeviceIdentity. Observations предоставляет доверенный collector, не устройство.
   В одной транзакции повторно проверяются grant/binding/revision/expiry/challenge,
   резервируются IP и место, затем challenge удаляется. Результат — lease в reserved,
   не подписанный профиль и не разрешение клиенту менять состояние ready.

Запрос привязан к случайному challenge записью в доверенной DB; отдельной подписи
полей request нет. Подмена challenge-ответа вне доверенного канала не входит в эту
гарантию. Nonce, подпись, private keys и SSH credentials не записываются в events.
Публичные bindings и выбранные параметры остаются в приватной базе.

Два конкурентных complete одного proof дают только один успех. При сбое до commit
операция откатывается целиком; ошибка capacity оставляет challenge пригодным до
expiry. После потери ответа успешного complete старый proof отклоняется: клиент
получает новый challenge для того же request_id, подписывает его и получает прежнюю
lease. Повтор не продлевает её срок. Любое изменение revision доступа требует нового
challenge; revoke/expiry запрещают даже повтор исторического запроса.

`reserve()` сохранён для доверенных внутренних вызовов и тестов; его нельзя публиковать
как API с произвольным device. `publishable()` остаётся моментальной проверкой:
атомарное подписание/публикация ещё не реализованы.

## Фоновый планировщик

`FleetScheduler(store, adapters).tick(limit=10, budget=30)`:

- Переводит до100 истёкших выдач в retiring; адреса ещё заняты.
- Перед каждой операцией проверяет monotonic deadline; максимум100 операций за tick,
  budget1–300с, по умолчанию10 операций/30с.
- `claim_work(hold=60)` атомарно закрепляет одну пару lease_id/generation за случайным
  token. До истечения60с другой scheduler её не получает. Claim сохраняется в DB.
- Сначала выбираются удаления, затем установки, с учётом next_at и возраста выдачи.
  Worker повторно проверяет доступ перед present и после receipt; подтверждение
  установки после конкурирующего revoke не делает выдачу готовой.
- Ошибка не освобождает адрес и не удаляет задачу: задержки5,10,20,40… до300с.
  После restart задержка сохраняется. Один ошибочный запрос не удерживает всю очередь.
- Удаление — новая generation, поэтому не наследует задержку/claim старой установки.
  Запоздавший finish с прежним token не перезаписывает новый claim.

Операция SSH ограничена адаптером25с. Deadline планировщика запрещает начинать новую
операцию, но не обрывает уже начатый эффект: tick может превысить budget на время
одной операции и локальных блокировок/DB-запросов. Это не hard realtime deadline.
Большая очередь может требовать сканирования/сортировки DB; ограничено число
обрабатываемых элементов, не худшее время SQL. Нет встроенного бесконечного loop,
systemd unit, jitter, общей circuit-breaker политики узла или автоматического scaling.

При падении worker новый процесс ждёт истечения claim. После истечения старый
процесс теоретически ещё может работать: безопасность удалённых эффектов обеспечена
[gateway fencing](fleet-gateway-fencing.ru.md), а не одним claim. SQLite/POSIX store
предназначен для процессов одного управляющего хоста, не для HA через сетевой диск.
`FleetWorker.once()` оставлен как низкоуровневый диагностический проход без backoff;
рабочий supervised loop должен вызывать Scheduler, не смешивать оба режима.

## Схема2 и миграция

Новый `initialize()` создаёт metadata.schema_version=2 и две таблицы:

| Таблица | Назначение |
| --- | --- |
| challenges | Hash nonce, device, revision прав, request, expiry |
| jobs | lease_id/generation, token, claim_until, attempts, next_at, фиксированный result |

Миграция существующей локальной схемы1: остановить все writers/старые workers,
сохранить приватную согласованную резервную копию, вызвать
`FleetStore(path).upgrade_services()`, проверить схему2 и сохранённые leases,
запустить новые процессы. Метод выполняет DDL и смену версии одной транзакцией,
повторный вызов безопасен. Автоматического обновления при открытии нет;
новый код отклоняет схему1, прежний код отклоняет схему2.

Это миграция локальной fleet DB, не перенос Friends/product DB. Старые leases,
registry history, request IDs и events сохраняются; gateway journal не меняется.
Обратной миграции нет. Не менять номер схемы вручную и не восстанавливать старую
базу поверх уже изменённых peers: требуется согласованное восстановление или
исправление вперёд. Пока production не обновлялся, серверный откат не требуется.

## Следующий результат

Подписанная выдача только после ready с проверкой доступа и revisions при публикации;
затем подключение к действующему входному протоколу/источнику прав, импорт старых
выдач и контролируемая установка. Также остаются автономный gateway TTL, TCP backend,
сервис запуска/recovery и мониторинг. Клиенты, HTTP API, платежи и Django UI в этом
checkpoint не изменялись. Единая админка остаётся пунктом7.1 после5/6.
