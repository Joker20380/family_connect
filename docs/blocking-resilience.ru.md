# Устойчивость к блокировкам: рабочие требования

24.09.2026 пользователь поручил учитывать сравнение конкурентов и усиливать защиту
всеми доступными способами. Требование принято для этапов5/6. Ниже — обязательные
направления работы, а не перечень уже включённых функций. Эффективность проверяется
по сетям; добавление технологии без измеримого выигрыша не является результатом.
[Источники сравнения](releases/2026-09-24-competitor-recovery.ru.md).

## Меры и приёмка

| Угроза | Работа | Проверяемый результат |
| --- | --- | --- |
| Блокировка UDP/сигнатуры протокола | Managed AWG3.1, отдельный TCP REALITY; исследование NaïveProxy, сравнение Hysteria2 | При отказе UDP работает TCP; каждый дополнительный транспорт даёт измеримый выигрыш |
| Блокировка служебного API | Независимые Reticulum ingress и резервный способ bootstrap/доставки | Недоступный основной API не мешает получить проверенную конфигурацию |
| Блокировка всех прежних наших IP | Перенос службы с сохранением identity и согласованного состояния, доступный независимый путь | Клиент получает новое назначение без ввода адреса/замены ключей |
| Потеря всех carrier paths | Внешний bootstrap, заранее подготовленные доверенные способы восстановления | Приложение различает невозможность доставки и ошибку VPN; нет обещания автоматического обнаружения без связи |
| Массовый сбор адресов | Адресная авторизованная выдача, ограниченные пулы рабочих/резервных назначений | Обычный подписчик не получает полный резервный каталог; отдельно оценивается атака множеством аккаунтов |
| Публичные RNS объявления | Не размещать в announces VPN-каталог/credentials; проверить закрытый discovery | Неавторизованный peer видит только предусмотренные метаданные; первый IP-hop остаётся видимым сетевому наблюдателю |
| Подмена/повтор обновления | Закреплённая подпись, шифрование per-device, expiry, revision/floor, previous hash | Подмена/устаревшая конфигурация не меняет VPN; повтор не вызывает повторное применение |
| Неработающий новый endpoint | Проверка туннеля и полезного трафика, rollback, ACK, ограниченные попытки/backoff | Не считать успешный TCP connect достаточной VPN-приёмкой; восстановить допустимое прежнее состояние |
| Смена Wi-Fi/мобильной сети, сон | Повторное обнаружение доступных путей, фоновые ограничения платформ | Восстановление без ручного переимпорта; измерить задержку и батарею |
| Общий отказ провайдера/региона | Разные failure domains и реальная резервная ёмкость | Резерв выдерживает перенос нагрузки; второй IP того же отказавшего пути не считается независимостью |
| Потеря контроллера при отзыве доступа | Автономный gateway TTL и durable reconcile | Истёкший доступ не сохраняется бесконечно; IP не освобождается до подтверждённого удаления |

## Порядок реализации

1.5.3а: schema/issuer/verifier AWG3.1 и общий corpus → native boundaries и capability
   binding для Android/Linux/Windows. Первый локальный checkpoint описан
   [здесь](releases/2026-09-24-managed-awg31.ru.md).
2. Продолжение5.2: verified ACK, безопасный offline→online перенос, действующая
   авторизация/импорт state; затем несколько независимых control ingress и bootstrap.
3.5.3б: стенд третьего транспорта; оценка совместимости/полезного трафика/ресурсов,
   выбор по измерениям. Не включать все runtime в продукт без такой проверки.
4.5.4/5.5/5.6 и6: native маршрутизация служебного канала вне неработающего VPN,
   переключение/rollback и все сценарии таблицы. Далее7.1 Django-админка.

Автоматический failover не должен переносить offline signing key на онлайн-сервер.
До реализации выбрать проверяемую схему заранее подписанных резервов либо отдельно
спроектированное ограниченное делегирование полномочий. Текущий локальный publisher
не решает offline→online перенос и не является готовым автоматическим сервисом.

## Метрики и границы

Фиксировать долю восстановления, P50/P95 времени, ручные действия, ложные переключения,
CPU/RAM/батарею/трафик, стоимость резерва. Сравнивать в одинаковых условиях и разделять
лабораторные отказы, российские домашние сети и мобильных операторов.
Не собирать содержимое пользовательского трафика или личные конфигурации в диагностику.

Ротация адресов не должна происходить беспричинно: она раскрывает резерв и нагружает
клиентов. Исходить из того, что выданный адрес может стать известен блокирующей стороне.
Reticulum, TLS-маскировка и платежи не гарантируют невидимость или недоступность сервиса
для противника. Ни один пункт таблицы не отмечается выполненным только по unit-тестам.
