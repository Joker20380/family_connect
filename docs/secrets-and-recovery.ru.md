# Критические секреты и аварийное восстановление

Решение24.09.2026. Это публичная схема хранения, без значений секретов и адресов
закрытого хранилища. Организация резервных копий ещё не выполнена.

## Где хранить

| Категория | Рабочее хранение | Восстановление |
| --- | --- | --- |
| Ключ подписи обновлений, корневые ключи выпуска конфигураций | Офлайн зашифрованное хранилище оператора; отсутствуют на серверах и в CI | Отдельный зашифрованный отключаемый носитель, пароль отдельно |
| SSH-доступы, пароли администратора, DNS/регистратор/хостинг, MFA recovery codes | Зашифрованное хранилище владельца, отдельные учётные записи и роли | Аварийная копия вне VPN-инфраструктуры |
| Секреты сервисов, серверные transport/RNS identities | Вне checkout/image, отдельные service accounts, минимальные права доступа | Зашифрованная копия вместе с описанием зависимостей и порядка восстановления |
| Product/Friends DB, fleet lease/IPAM/fencing state, revocations и журнал выдачи | Закрытое серверное хранилище с доступом нужной службы | Согласованные зашифрованные резервные копии, проверка восстановления |
| Приватные ключи клиентов | Keystore/DPAPI или защищённое локальное хранилище конкретного клиента | По отдельному протоколу платформы; не обещать восстановление неэкспортируемых ключей |
| Схемы, код, публичные anchors, обезличенные инструкции | Git | Обычная копия репозитория |

Пароли хранилища и recovery codes не передавать в чат, tickets, CI variables или
репозиторий. Пользователь выбрал компьютер и отдельный офлайн-носитель. Конкретный продукт,
подготовка носителя и порядок доступа владельца ещё не настроены.
Ключ расшифрования резервной копии не хранить только на резервируемом сервере.
Одной папки с chmod или .gitignore недостаточно для защиты копии диска.

Для серверного процесса секрет должен быть доступен во время работы: это не защита
от полного захвата root. Минимизировать полномочия и распространение ключей;
root signing keys не выдавать рабочим процессам. Не переносить существующие ключи
без проверки совместимости и восстановления. Этот документ не выполняет миграцию.

## Что записывать в закрытом реестре

Для каждого секрета: назначение, владелец, службы-потребители, где рабочая и резервная
копия, способ восстановления, дата проверки, порядок отзыва/ротации. В публичном Git
хранятся только категории и шаблон, не реальные значения/инвентарь инфраструктуры.
В закрытом runbook также нужны доступ к DNS/хостингу, версии ПО и команды развёртывания.

Резервирование должно сохранять согласованность identities, revocations, выданных
revision/sequence, lease/IPAM/fencing и доверенных anchors. Восстановление старой базы
не должно повторно выдавать занятые адреса или допускать replay. После потери узла
сначала исключить его повторное управление, затем восстанавливать state и доступ.
Сохранение RNS identity не заменяет достижимый независимый ingress.

Проверять восстановление на изолированном стенде. Фиксировать дату и результат без
секретов. При компрометации нужен отзыв/ротация и обновление доверия клиентов,
а не простое восстановление прежнего ключа из backup.

## Правила публикации

Не публиковать runtime state, базы/дампы, private keys, .env, invitation codes/URLs,
готовые VPN-профили, содержимое сообщений, пароли, закрытые инструкции доступа.
Проверять список staged-файлов и содержимое diff перед push; автоматический поиск
известных шаблонов не доказывает отсутствие всех секретов. TEST ONLY vectors могут
содержать заведомо публичный синтетический ключ, но не производственный материал.
Не выводить совпавшие значения в лог проверки. При обнаружении уже опубликованного
секрета сначала отозвать/заменить его: удаления последним коммитом недостаточно.

IP первого VPN-hop и клиентская конфигурация доступны самому подписчику; нельзя
строить защиту на обещании скрыть их от всех. Учётные данные и закрытые ключи
должны оставаться секретными независимо от известности адреса сервера.

## Автоматическая проверка перед коммитом

После `git add` выполнять `python3 scripts/check_public_sources.py`. Проверяются
именно blobs индекса, не незакоммиченные рабочие файлы. Вывод содержит пути и категории,
но не совпавшие значения. Отказ: runtime state paths, .env (кроме example/template),
ключевые контейнеры/БД/APK, PEM private keys, известные GitHub/AWS/Slack credentials,
строки WireGuard PrivateKey. Необычные entries (symlink/submodule/conflict) требуют
отдельного рассмотрения и по умолчанию блокируются.

В CI проверка входит в job tests workflow phase0. CI запускается уже после загрузки
в GitHub: он не предотвращает первоначальную утечку. Поэтому локальная проверка до
commit/push обязательна. Это не обязательный серверный push protection и не полный
аудит истории или всех форматов секретов; base64/JSON/архивы и неизвестные токены
могут пройти. Публичные TEST ONLY identity vectors проверяются отдельно при ревью.

Узкое исключение — нулевой WG key в двух существующих desktop parser tests;
другой ключ в тех же файлах отклоняется. Общего исключения для tests/docs нет.

Проверка рабочего места24.09: есть GPG, отсутствуют keepassxc/age/cryptsetup в PATH;
съёмного блочного носителя не обнаружено. Это не аудит всех установленных программ.
Реальное хранилище и backup ещё не созданы. Подключение отдельного носителя и ввод
пароля владельцем выполняются до переноса секретов; пароль не передавать в чат.

## Локальное хранилище KeePassXC

24.09 установлен KeePassXC2.7.10 из Ubuntu repository. Формат — зашифрованный KDBX;
расположение вне checkout/Git, точный локальный путь в публичных отчётах не публикуется.
Права: личный каталог0700, база0600. Мастер-пароль вводит владелец в локальном окне;
он не передаётся в чат, аргументы команд, логи или репозиторий. Ключевой файл не создан:
восстановление требует базы и мастер-пароля. Носитель будет добавлен отдельным шагом.

Структура: Administration, Server secrets, Offline signing keys, Recovery procedures,
Backup inventory. Названия разделов — схема; это не подтверждение переноса секретов.
Факт создания и проверки базы фиксируется отдельным датированным отчётом.
Сам ноутбук с интернетом не является физически офлайн signing station: наличие
зашифрованной базы не меняет ограничения на использование root signing keys.

Файлы `.kdbx` и `.keyx` исключены через .gitignore и блокируются source guard даже
при принудительном добавлении. Шифрование не является разрешением публиковать базу.
Пароль восстановления следует сохранить отдельно: резервная копия базы без пароля
не обеспечивает восстановление. Потеря ноутбука до создания внешней копии остаётся
риском; локальная база ещё не заменяет выбранный офлайн-носитель.

[Официальное руководство KeePassXC](https://keepassxc.org/docs/KeePassXC_GettingStarted).

## Переход к полному управлению секретами

`.env`, как в Django, отделяет параметры от кода, но хранит значения открытым текстом.
Сам по себе .env не заменяет шифрование, разграничение доступа или резервирование.
Для каждого секрета различать состояния: обнаружен → зашифрованная копия → проверено
извлечение → потребители переведены → старые копии отозваны/устранены.

1. Локальная копия: завершена24.09 для203 файлов выбранного проектного runtime state;
   [результат импорта](releases/2026-09-24-vault-import.ru.md). Это не все секреты
   ноутбука и не текущая резервная копия серверов.
2. Реестр потребителей: для signing/enrollment/VPN ключей указать инструменты,
   требуемый формат и путь передачи. Сам приватный реестр остаётся в KeePassXC.
3. Инструменты оператора: получение нужного секрета только на время операции,
   без argv/logs/постоянных plaintext export. Сначала тест на synthetic key,
   затем проверка настоящей операции без изменения опубликованных артефактов.
4. Серверные службы: инвентаризация на разрешённых FC hosts, отдельные service users,
   files/credentials вне checkout/image; root signing keys остаются локально.
   Наличие `EnvironmentFile` или .env не означает защиту от root. Не менять пути
   без проверки restart, rollback и доступа процесса.
5. Резервирование: отдельный офлайн-носитель, проверка открытия и восстановления
   согласованных DB/revision/revocation/fencing данных. Копия на том же диске
   не защищает от потери ноутбука.
6. Устранение лишних открытых копий: только после перевода потребителей и проверки
   восстановления. Удаление файла на SSD не доказывает физического уничтожения;
   при подозрении на раскрытие нужна ротация и, где применимо, миграция доверия.

Критерий завершения: у каждого производственного секрета известны владелец,
потребители, рабочее место хранения, проверенная резервная копия и процедура ротации;
нет необъяснённых plaintext копий в checkout, artifacts, logs или CI. Сейчас этот
критерий не выполнен: импорт в KeePassXC не удалял рабочие оригиналы.
