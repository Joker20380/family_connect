# Windows TCP: сессия службы, маршруты и DNS

Сетевая сессия реализована в Windows broker, но TCP-движок ещё не включён в обычный
installer и TCP не выведен в GUI. При отсутствии фиксированного каталога `{app}/tcp`
команда возвращает `tcp-engine-missing`. Нельзя копировать непроверенный движок или
подменять опубликованный installer0.2.9. Упаковка и UI — следующий этап.

## Контракт службы

- `activate-tcp`: прежний подписанный профиль, привязанный к устройству, DPAPI LocalSystem.
- `connect-tcp`: проверяет владельца, отсутствие другого активного транспорта и наличие
  профиля/движка; отвечает `pending`, настройка выполняется асинхронно.
- `status`: `pending` во время запуска/очистки, `on` после настройки адаптера и при живом
  Xray; поле `transport=tcp`. Это не подтверждение внешнего доступа или REALITY handshake.
- `disconnect`: владелец может отменить запуск или остановить сессию. Переход в отключённое
  состояние происходит после очистки, проверяется следующим status.
- Другой SID видит `other-user` и не может остановить/заменить сессию. WG connect и замена
  активации запрещены во время активного/запускающегося TCP.

`tcp-engine-exited` означает неожиданное завершение Xray; `tcp-session-failed` — ошибку
запуска/настройки; `tcp-cleanup-required` — неподтверждённую очистку. Последняя сохраняет
состояние pending и блокирует новый старт. При повторном запуске службы сначала
восстанавливаются настройки по журналу; ошибка очистки не скрывается.

## Сетевые изменения

Фиксированный PowerShell-скрипт встроен в assembly. Служба передаёт операции и имя
адаптера JSON через stdin; пользовательские команды, пути и окружение через IPC не
принимаются. Имя адаптера — случайное `fctcp` +8 hex. PowerShell и Xray принадлежат
Job Objects, закрываемым при смерти службы. JSON передаётся после включения в job.
Обмен с помощником использует UTF-8, включая названия физических адаптеров.

Перед изменениями проверяются конфликты создаваемых маршрутов и действующая NRPT policy.
Пока существующая DNS policy в обычной сборке приводит к отказу старта: объединение с
корпоративными/GPO-правилами не реализовано. Прежние правила не перезаписываются.

Служба выбирает текущий IPv4 uplink до создания TUN. Xray получает его имя в
`sockopt.interface`: исходящий транспорт закрепляется за этим интерфейсом, чтобы
не попадать обратно в TUN. Привязка к loopback проверяется локальной CI fixture;
полноценный physical-uplink/full-tunnel REALITY сценарий ещё требует приёмки.

На собственном TUN: IPv4 `10.79.0.2/32`, IPv6 `fd79:fc::2/128`, MTU1280, metric5;
маршруты `0.0.0.0/1`, `128.0.0.0/1`, `::/1`, `8000::/1` создаются в ActiveStore.
Существующие default routes и параметры физических интерфейсов не заменяются.
DNS на TUN — `1.1.1.1`; отдельное NRPT-правило для `.` имеет уникальное имя с alias.
Готовность адресов проверяется по AddressState=Preferred, затем проверяется процесс.
Проверка IPv6/внешнего DNS/full-tunnel и взаимодействия с политиками Windows перед
широким распространением остаётся обязательной. Kill switch/WFP здесь не добавлялся.

## Остановка и восстановление

Перед созданием Xray/маршрутов/DNS записывается атомарный журнал
`%ProgramData%/FamilyConnect/tcp-session.json` в закрытом каталоге LocalSystem/Admins.
Он содержит только версию и уникальное имя адаптера, без профиля и ключей.

Очистка сначала завершает Xray, затем удаляет только своё NRPT-правило с совпадающими
DisplayName/Namespace/NameServers и остатки своих адресов/маршрутов/DNS на своём TUN.
Удаление адаптера подтверждается. После успешной очистки удаляется журнал.
При несовпадении владельческих признаков правило не удаляется, журнал сохраняется.

Падение Xray замечает worker. При смерти broker ядро Windows закрывает job и
останавливает дочерние процессы. SCM настроен на перезапуск службы (1/5/10 секунд);
OnStart сначала выполняет очистку по журналу, затем открывает IPC. VPN автоматически
не переподключается. После отключения питания очистка выполняется при следующем старте.
Остановка службы ожидает завершения worker; installer получил увеличенное ожидание
службы, чтобы не прервать нормальную очистку.

## Изолированная приёмка

Отдельный SessionHost компилирует реальные Broker/Store/Native/TcpSession/TcpNetwork/
TcpEngine/ProcessJob с `TCP_SESSION_TEST`. Он действительно работает от LocalSystem
через SCM и штатный named pipe. Тестовый профиль подписывается временным ключом и
хранится через DPAPI. Контур не использует пользовательские профили или gateway.

Тестовый режим отличается фиксированными адресами/маршрутами
`198.18.0.1/32`, `fd79:fc::1/128`, DNS namespace `.fctcp-ci.invalid` и локальным VLESS
вместо REALITY. Метрика TUN5000 сохраняет обычное DNS-предпочтение runner вне тестового
домена. Запросы Windows resolver проходят через NRPT/TUN/VLESS к локальной UDP fixture;
HTTP-запросы проверяются отдельно через IPv4 и IPv6. Стандартная сборка не включает
этот символ и не принимает тестовый режим из IPC/профиля/окружения.

Сценарии: disconnect, engine crash, broker crash/restart, service stop/start,
отмена запуска. Отдельная обычная Windows-учётная запись проверяет запрет действий
над чужой сессией. После каждого сценария сверяются default routes, DNS и NRPT,
отсутствие TUN/маршрутов/журнала. Учётная запись и служба удаляются по завершении.

Устройство пользователя и сервер не изменяются. Отложенные пользователем сетевые/
нагрузочные испытания не возобновляются этой CI-приёмкой.

Источники: [NRPT](https://learn.microsoft.com/en-us/powershell/module/dnsclient/add-dnsclientnrptrule),
[маршруты](https://learn.microsoft.com/en-us/powershell/module/nettcpip/new-netroute),
[Xray Windows socket binding](https://github.com/XTLS/Xray-core/blob/d2758a023cd7f4174a5a5fa4ff66e487d4342ba0/transport/internet/sockopt_windows.go).
