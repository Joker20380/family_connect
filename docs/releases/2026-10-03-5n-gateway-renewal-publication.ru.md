## Atomicity, failure and repetition

Before rename, validation, metadata, service-read, fsync or rename failure preserves
the old target and cleans the operation's own temp where possible. Wrong temp owner
is rejected before publication; normal operation never publishes root0600 then repairs.
An intervening writer is detected and not overwritten; callers serialize existing sync.

After rename, final-readback/directory-fsync failure is explicitly FAIL with
`published=true`; the operator cannot claim the old inode remains. Receipt persistence
failure is not success and requires destination inspection before retry. It does not
silently roll security state backward. Any rollback must retain monotonic CRL/floors;
an expired prior credential cannot be presented as a healthy fallback.

Same validated bytes with a fresh receipt are a verified no-op, preserving the inode.
Existing receipt path is rejected rather than blindly replayed. No automatic retry or
renewal policy added. Successful live execution required no credential rollback.
