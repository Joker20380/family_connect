## Новые правила

| Приоритет | Семейство | Назначение |
|---|---|---|
| 10627 | IPv4 | Адрес VPN-сервера /32 → таблица main, независимо от socket mark |
| 10628 | IPv4 | Prohibit для того же /32, если main не нашла маршрут: не допустить возврат в TUN |
| 10629 | IPv4/IPv6 | lookup main suppress_prefixlength 0: сохранить более точные LAN/Docker/другие маршруты |
| 10630 | IPv4/IPv6 | Остальной непомеченный трафик → таблица 64630 с default через TUN |

Mark 64630 для внешних соединений Xray сохраняется. Системная local table остаётся
выше этих правил. Более точные маршруты main намеренно имеют приоритет, как в AWG;
это не утверждение, что абсолютно каждый IP-пакет хоста отправляется в VPN.
Gateway пока только IPv4, согласно строгой схеме пилотного профиля.

Проверяются конфликты всех четырёх приоритетов и таблицы 64630 до записи ownership marker.
Новый root-owned marker хранит id и endpoint, чтобы очистка использовала исходный gateway.
Удаляются правила с точными selector/table/priority, без глобального flush.
Legacy marker прежнего установленного helper также поддерживается и владеет только
старыми правилами 10630. При неудачном удалении правил/собственного default route marker
сохраняется для повторной очистки. Процесс Xray завершается даже при ошибке cleanup.

## Проверки

`scripts/check_tcp_routes.py` запускается только в контейнере с `--network none` и
NET_ADMIN, проверяет начальный набор интерфейсов `{lo}` и создаёт тестовые dummy links.
Все операции iproute2 и выбор маршрутов выполняет настоящее ядро отдельного namespace.
Проверены public IPv4/IPv6, LAN и Docker routes, loopback, обход gateway с меткой/без неё,
исчезновение uplink default без возврата gateway в TUN, отказ при конфликте приоритета,
сохранность чужого правила, неправильный owner, частичный запуск, повторная очистка
после имитированного сбоя удаления, совместимость со старым marker и идемпотентность.

Контейнер не подключался к интернету или VPN-серверу, не монтировал host network namespace
и не менял маршруты ноутбука. Вызов `resolvectl revert` заменён тестовой заглушкой:
проверка DNS/systemd в этом стенде не заявляется. Полный lifecycle systemd/SIGKILL,
реальный RST и передача пользовательского трафика здесь не проверялись: проверен
выбор маршрута для немаркированного gateway destination и очистка частичного состояния.

Изолированный тест прошёл. Полный Python-набор: **222 passed**, два прежних предупреждения
FastAPI/Starlette. UI не менялся, GTK повторно не запускался. Namespace-тест добавлен в
TCP CI workflow; удалённый GitHub CI ещё не запускался, push/release не выполнялись.

## Реальный трафик в отдельном контейнере

Первый прогон: 24 раунда с паузой 2 секунды, параллельно TUN HTTPS, SOCKS HTTPS
и UDP DNS через TUN. Результат: **TUN 24/24, SOCKS 24/24, UDP DNS 23/24**;
правила удалены, Xray завершён, TUN исчез. Неуспех DNS дал ненулевой exit code.
Это ограниченная проверка, не доказательство исправления всех прежних тайм-аутов.
TUN использует штатный probe_interface с резервным HTTPS endpoint; SOCKS проверяет
один numeric HTTPS endpoint. Это контролируемая нагрузка, но не идентичные HTTP-пробы.

Повторный тест `scripts/check_tcp_traffic.py` добавляет DNS TCP через TUN и прямой
UDP DNS с socket mark 64630; всего пять параллельных проб в каждом из 24 раундов.
DNS проверяет example.com через 1.1.1.1, timeout 3 секунды. HTTPS проверяет также
ожидаемый egress IP. Скрипт выводит только счётчики, тип ошибки и номер раунда;
профиль и ключи не выводятся. Контейнер имеет собственный bridge namespace,
NET_ADMIN и /dev/net/tun, без host network. Это не проверка системного resolved.

Воспроизведение: собрать образ согласно TCP workflow, смонтировать clients/linux
в /fix, clients/desktop в /desktop, scripts в /checks (read-only), приватный каталог
с linux.conf в /keys (read-only); запустить образ с --rm --user 0 --cap-add NET_ADMIN
--device /dev/net/tun --entrypoint python3 и /checks/check_tcp_traffic.py.
Live-тест требует секретный профиль и потому не добавлен в публичный CI.

Результат повторного прогона: **TUN HTTPS 24/24, SOCKS HTTPS 22/24,
TUN UDP DNS 23/24, TUN TCP DNS 22/24, прямой UDP DNS 22/24**. Cleanup прошёл.
В раунде 10 отказали SOCKS и TCP DNS; в раунде 18 — SOCKS и все три DNS-пробы;
в раунде 23 — только прямой DNS. DNS-ошибки — TimeoutError около 3 секунд;
SOCKS — проверка curl/egress не прошла после 3.012 и 5.016 секунд. Код curl отдельно
не сохранён, поэтому фазу этих HTTPS-ошибок по этому результату определить нельзя.
Тайм-ауты прямого DNS показывают проблему за пределами только TUN, но не доказывают
блокировку РКН, неисправность сервера или общую первопричину. Прямой HTTPS-контроль
в этой серии отсутствовал. После прогона в сохранённый скрипт добавлен явный Docker
preflight; его синтаксис проверен, сама нагрузка выполнена до этой проверки окружения.
