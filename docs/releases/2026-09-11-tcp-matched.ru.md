## Методика

`scripts/check_tcp_matched.py`: отдельный Docker bridge namespace, NET_ADMIN и TUN.
Явные проверки Docker и начального набора интерфейсов lo/eth0. Не используется host
network, не изменяются маршруты ноутбука. Локальный приватный профиль монтируется
read-only, конфигурация Xray создаётся внутри контейнера с правами 0600.

24 раунда, пауза 2 секунды, пять параллельных проверок:
- Один и тот же GET https://1.1.1.1/cdn-cgi/trace напрямую, через TUN и через SOCKS.
- UDP DNS example.com через 1.1.1.1 напрямую и через TUN, timeout 3 секунды.

Во всех HTTP-пробах один curl, connect-timeout 3 и max-time 5 секунд, без повторов
и резервного endpoint. Проверяются exit code и HTTP 200; тело не сохраняется,
выходной IP здесь не проверяется (проверялся предыдущим live-тестом).
Прямой curl работает под UID 65534: тестовое правило 10500 направляет этот UID в main;
выбор eth0 проверен через реальный ip route get. Прямой DNS использует socket mark.
Правило UID и маршруты TCP удаляются, процесс Xray завершается, отсутствие TUN проверяется.

Каждые 250 мс плюс длительность команды снимается ss -tin только к адресу VPN-сервера.
Сохраняются число SYN-SENT/ESTAB, значения retrans и RTO, без адресов, портов и ключей.
Это дискретные снимки, не pcap и не привязка конкретного внешнего сокета к HTTP-запросу.
Тайминги curl: connect, appconnect, starttransfer, total (секунды). В TUN и SOCKS
локальное установление соединения не равно завершению внешнего TCP/REALITY handshake.

## Вывод и следующий шаг

Ошибка HTTPS теперь сохранена с кодом и фазой. Есть признаки задержек внешнего TCP
к VPN-серверу, одновременно с медленным HTTPS через него. Это корреляция, а не
доказательство причины: клиентский ss не показывает, что видел сервер и где потерян пакет.
Потери одиночных DNS-запросов наблюдаются и на прямом пути. Здесь не проверяются
повторные запросы/переключение DNS системным resolved, работа приложений и полная
устойчивость VPN. Причастность РКН не установлена.

Следующий шаг: короткая синхронная запись только TCP-заголовков на клиентском контейнере
и разрешённом сервере 185.251.89.19, с привязкой времени и потока. Сопоставить приход
SYN, ответ SYN-ACK и подтверждение ACK, затем задержки данных; собрать контрольный
HTTPS с самого сервера. До этого не менять тайм-ауты и не начинать длительный host-тест.
После локализации — короткая проверка установленного helper с backup, затем AWG → TCP recovery.
