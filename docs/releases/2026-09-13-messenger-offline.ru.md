# Offline-доставка и безопасное удаление сообщений — 13.09.2026

База: d77b22217abd5f017428d32c650865b0c7a10b27. LXMF1.1.1, RNS1.5.1,
cryptography46.0.7 неизменны. APK не упаковывались, версии приложений не менялись;
рабочие серверы и пользовательские ключи не затрагивались.

## Что изменилось

- Явная PROPAGATED-отправка и статус `relayed`: приём узлом не выдаётся за доставку
  адресату. DIRECT по умолчанию сохранён. Повтор использует тот же подписанный payload.
- Новый `messenger/mailbox.py`: доверенный node public key, отдельный link с
  ожиданием establishment callback, идентификация chat identity и конечный budget.
- Получение: decrypt → проверка контакта/подписи → durable Store commit → удаление
  с propagation node. При ошибке записи purge не отправляется. При неизвестном
  отправителе/неподдерживаемом содержимом ciphertext сохраняется на узле.
- Повтор после отказа доступа открывает свежий link. Синхронизация сериализована,
  отмена/выход закрывают link; лимиты:1000 IDs,10 сообщений,48KB запрошенного объёма,
  70KB response,12s сетевой бюджет (до30s). fsync не имеет жёсткого realtime deadline.

## Почему понадобился отдельный путь получения

В исходниках закреплённого LXMF1.1.1 `lxmf_delivery()` записывает dedupe ID,
перехватывает исключение application callback и возвращает успех. Затем
`message_get_response()` отправляет haves для удаления с узла. Ошибка записи в
историю приложения могла оставить получателя без локального сообщения и без
копии на узле. Также `set_retain_node_lxms(True)` не предотвращает purge в этой
ветке `message_get_response()`. Наш Mailbox не использует эти download callbacks.

Первый стенд со штатным download API получил отказ доступа, затем не завершил
повторный fetch в40s. Причину конкретного зависания до конца не локализовали;
известно, что API может удерживать ссылку на закрытый link до фоновой очистки.
Не заявляем, что единственной причиной был этот механизм. Новый путь со свежим
link прошёл denial→allow→fetch на том же процессе без увеличения timeout.

## Реальная локальная приёмка

Три независимых процесса (Alice, propagation node, Bob), TCP только127.0.0.1.
Bob остановлен до отправки. Node получил ciphertext; sender получил `relayed`.
Alice и node остановлены, node поднят заново с прежней identity и очередью.
Bob поднят с прежними identity/контактами. Скачивание до allow отклонено. После
allow искусственный OSError при записи не удалил копию с узла. Повтор после
устранения ошибки сохранил сообщение. Перезапуск Bob и повторное скачивание
не создали дубль. Отдельные варианты завершения:

1. Уменьшение storage limit до1 байта и upstream cleaner: очередь очищена.
2. Искусственное старение timestamp в именах синтетических spool-файлов более
   чем на стандартные30 дней, upstream cleaner: очередь очищена.
3. Повторное получение уже сохранённого сообщения с delete_after_store=True:
   duplicates1, purged1, очередь узла пуста, локальная история сохранена.

Ciphertext не содержит синтетический текст/маркер; префикс адреса получателя
остаётся открытым, как предусмотрено LXMF. Это проверка поведения закреплённой
реализации, не внешний криптографический аудит. Реальный PoW cost13/validation
не отключался; fixture использует upstream single-worker вычисление вместо
multiprocessing, чтобы не запускать worker на каждое CPU машины.

Фокусная offline-приёмка:3 passed,41.40s. Фокусные проверки core/mailbox:22 passed,
0.34s. Дополнительно проверены неверный ciphertext, неизвестный контакт, отмена,
ошибка записи, порядок commit-before-purge и освобождение link/lock.

Промежуточные ошибки стенда: неверный путь spool (в LXMF он содержит `/lxmf/`),
неверный импорт MESSAGE_GET_PATH (нужен класс LXMPeer из одноимённого модуля).
Исправлены; успешные результаты приведены выше, не скрывая исходных отказов.

## Что ещё не сделано

Нет развёртывания propagation node в Amsterdam, Android UI/Keystore, автоматического
poll/retry, прикладного ACK отправителю, Sideband acceptance и полной службы/lifecycle.
Скачивание защищено allowlist; anonymous upload с PoW штатный LXMF допускает.
Upstream storage limit — очистка после приёма, а не admission limit/жёсткая квота.
До Amsterdam нужны ограничение приёма, отдельный OS user/service, дисковый лимит,
retention-конфигурация и ограниченный пилот. Приватный каталог сам по себе не
делает test fixture готовым сервером. Размер VPS сейчас не менялся.

Следующий шаг: ограничить приём на пилотном узле и проверить квоты под нагрузкой;
затем Android key/lifecycle и экран чата. TCP adverse-network измерения остаются
отдельным следующим пунктом транспортного плана.
