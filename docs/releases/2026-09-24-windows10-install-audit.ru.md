# Windows 0.2.13: сбой первой установки на Windows 10

Пользователь сообщил о первой установке: `Runtime error (at 5:536): Cannot
install Family Connect service`. После ошибки sc.exe сообщил, что служба не
установлена. На фото Windows 10 Pro 22H2, build 19045.2364. По сообщению
пользователя установка на Windows 11 накануне прошла.

Проверен исходный commit `c2984363222c1547917337bb5b66ea12bb992522`.
setup.iss/Native.cs/Program.cs/build.ps1 совпадают с текущими рабочими файлами.
Локальная копия опубликованного EXE: 49934846 bytes, SHA256
`88f4274cd2aff07a73a5366f09b2f37301ccd442a67574a30eeaf7c587d4ae5b` — совпадает
с каталогом выпуска и сохранённой публичной проверкой от 23.09.2026.
Повторная загрузка публичного EXE в этом аудите не выполнялась.

GitHub API повторно подтвердил success Windows job run35921509278, включая
Install application and service, driver, broker, URI и uninstall. Workflow
использует windows-latest, отдельного Windows 10 job нет. В build-check.txt
подтверждено включение coreclr.dll, hostfxr.dll, hostpolicy.dll и runtimeconfig;
build.ps1 публикует self-contained win-x64. Не следует предлагать отдельную
установку .NET без признаков отсутствующей зависимости.

Подтверждён дефект диагностики: Inno Setup не показывает ExitCode/ошибку Exec;
Program.cs перехватывает исключение /install-service и возвращает только1.
До создания службы выполняются загрузка runtime, проверка администратора и
Store.SecureRoot. Сам sc create тоже может отказать. Отсутствие службы после
ошибки не определяет точную первопричину и не исключает последующий откат.

Подготовлен [CMD для повторной установки с журналом](../diagnostics/windows-install-log.cmd).
Положить рядом с установщиком0.2.13, запустить от администратора; после закрытия
установщика откроется уникальный каталог TEMP с setup.log, host trace (если
runtime успел его создать), версией ОС и состоянием службы. Профили/ключи скрипт
не читает. Это повтор установки с диагностикой, не read-only проверка.
В Windows скрипт ещё не исполнялся; Linux-проверка ограничена просмотром команд.

Причина на конкретном ПК остаётся открытой: требуется журнал, затем исправление
и проверка на Windows 10. Нового EXE, изменения версии или публикации нет.
Rollout/rollback не выполнялись, публичный Windows канал остаётся0.2.13/sequence9.

## Полученные журналы повторной установки

Пользователь передал setup.log и dotnet-host.txt. Setup24.09 23:27 (+03)
подтверждает x64/build19045, Administrative и остановку в PrepareToInstall:
`Cannot stop Family Connect services`. Это повторный запуск поверх файлов,
оставшихся от первой попытки, а не журнал исходного ssPostInstall.

Host trace подтверждает `/remove-service`, self-contained .NET10.0.12,
загрузку hostfxr/hostpolicy и заканчивается `Loaded library from ... coreclr.dll`.
Явного HRESULT, exit code или managed exception в этих двух файлах нет.
Подозрение на аварийное завершение при инициализации CLR, но точная причина
ещё не доказана; отсутствие .NET и отсутствие административных прав этим
запуском не подтверждаются. Не отключать защиту и не менять runtime наугад.

Подготовлен [read-only сборщик crash records](../diagnostics/windows-crash-log.cmd):
Windows PowerShell5.1, CPU/OS, Application events1000/1001/1026 за7 дней,
только записи с FamilyConnect, до30 записей, чтение per-app mitigation settings.
Повторной установки/запуска VPN, изменения служб и защитных настроек нет.
Нужен полученный TXT; скрипт просмотрен статически, на Windows здесь не запускался.
Исходные пользовательские журналы в Git не копировались.

## Crash report: подтверждён CLR failure, CET — основная гипотеза

Полученный FamilyConnect-crash TXT: Intel Core i5-11300H, Windows10 Pro
19045.2364; повторяющиеся Application Error1000 для FamilyConnect0.2.13.0,
KERNELBASE10.0.19041.2364, exception0x80131506, offset0x10fe32.
Это внутренний сбой CLR; код не устанавливает конкретную первопричину.
В совокупности с host trace сбой происходит при запуске runtime.
Выгрузка содержит только1000: более подробного CLR assertion/stack нет.

Основная гипотеза — известный конфликт CET новых .NET со старыми патчами
Windows10. Разработчик .NET описал исправление системными обновлениями:
https://github.com/dotnet/runtime/issues/108589#issuecomment-2396857957
Автор issue подтвердил Win10 Pro19045.2965 и CETCompat=false:
https://github.com/dotnet/runtime/issues/108589#issuecomment-2399641501
Это внешний аналог, не подтверждение CET на пользовательском ПК.

Рекомендуемый следующий шаг: накопительные обновления Windows10 через
Windows Update, перезагрузка, повторная установка0.2.13. Смена ОС на Windows11
не является предложенным действием. Защита CET не отключалась, бинарники
не заменялись. При невозможности обновления — отдельная проверка гипотезы
совместимости; не выпускать новый установщик с отключённой защитой на основании
одного общего exception code. Runtime/installer исправление пока не подтверждено.
