# TCP-заголовки на двух концах — 11.09.2026

Продолжение [сравнения одинаковых запросов](2026-09-11-tcp-matched.ru.md).
Использован исправленный helper экспериментальной ветки pilot/tcp-reality-2026-09-11.
На хосте он по-прежнему не установлен. Linux 0.2.7, опубликованный desktop 0.2.8,
сервер 0.2.1 и TCP Xray 26.3.27 остаются прежними. Конфигурация сервера не менялась.

## Методика и границы

Клиент: прежние 24 раунда одинаковых HTTPS direct/TUN/SOCKS и UDP DNS direct/TUN,
в одноразовом Docker bridge namespace. На клиентском eth0 и внешнем интерфейсе
разрешённого сервера 185.251.89.19 одновременно запущен ограниченный AF_PACKET-сбор.
На сервере фильтр peer берётся из SSH_CONNECTION, на клиенте — из приватного профиля.
Фильтр IPv4 TCP/443. Сохраняются только время, направление, порты, seq/ack, flags и
длина данных. Payload никогда не записывается. Максимум 30000 записей и 115 секунд.
Сервер параллельно выполняет 30 HTTPS-запросов к 1.1.1.1 с интервалом 3 секунды.

Первый запуск выявил ошибку измерителя: ETH_P_IP получил только входящие пакеты.
Его нельзя использовать для вывода об отсутствии исходящих SYN/SYN-ACK. Он сохранён
отдельно как неполная проба: HTTPS direct/TUN/SOCKS по 23/24, DNS оба 24/24,
серверный HTTPS 30/30. После исправления на ETH_P_ALL (с IPv4-фильтром в парсере)
выполнена новая серия с обоими направлениями.

Начальные SYN сопоставляются между концами по TCP sequence, позволяющему пережить
NAT с изменением source port. SYN-ACK сопоставляется по ACK=ISN+1. Времена handshake
считаются внутри одних часов: клиент SYN→SYN-ACK, сервер SYN→SYN-ACK и SYN-ACK→ACK.
Абсолютная синхронизация часов между машинами не предполагается. В HTTP-измеритель
добавлен started_wall для соотнесения событий и раундов на клиенте.

Сбор не сообщает kernel packet-drop counters; отсутствие записи не доказывает потерю
в сети. Данные TCP могут объединяться/сегментироваться offload, поэтому анализатор
не выводит процент потерь payload из количества записей. Привязки отдельного Xray
socket к конкретному запросу TUN/SOCKS/DNS нет: одновременно работают три запроса.
Это локализует наблюдаемый интервал, но не источник сетевой неисправности.

## Результаты

Полная серия: HTTPS direct 24/24, TUN 24/24, SOCKS 23/24; UDP DNS direct/TUN
по 24/24; серверный HTTPS 30/30. Cleanup прошёл, тест вернул exit 1 из-за одного
SOCKS SSL connection timeout (curl 28, раунд 7, 3.000512 секунды).

Захвачено 2486 клиентских записей (1268 исходящих) и 2596 серверных (1265 исходящих).
Все 72 начальных TCP-соединения сопоставлены: у каждого есть SYN на сервере и SYN-ACK
на клиенте. В двух соединениях клиент повторил SYN; обе копии видны на сервере,
а обе копии SYN-ACK видны на клиенте. Это наблюдение задержки, не доказательство потери.

Медиана клиентского SYN→SYN-ACK — 0.049005 секунды. Максимальная задержка ответа
SYN→SYN-ACK на сервере во всей серии — 0.000846 секунды. Три соединения, начавшиеся
в раунде 7, показали клиентские интервалы 1.314923, 0.787732 и 1.308216 секунды;
серверные интервалы ответа — соответственно 10, 9 и 73 микросекунды.
Сервер SYN-ACK→подтверждающий ACK: 1.261971, 0.696461 и 1.260295 секунды.
Таким образом, задержка этого этапа не объясняется медленной обработкой SYN сервером.
Она находится в пути между точками захвата, включая сеть хоста/виртуализацию,
Wi-Fi/роутер, внешний маршрут и возможные задержки планирования самого измерителя.

После тестов ip route get для 185.251.89.19 и 1.1.1.1 показал main/wlp0s20f3,
интерфейс Wi-Fi. Это снимок после измерения, а не непрерывный журнал маршрута.
Wi-Fi как первопричина не доказан. Проверка маршрута сначала упёрлась в sandbox;
повторный read-only запрос вне sandbox выполнен после случайной отмены пользователем.
Это не меняло маршруты и не требовало повторного сетевого теста.

Docker/root SSH к единственному разрешённому серверу и локального профиля

в /tmp-версии, финальное изменение путей проверено компиляцией Python.

результат 222 passed. Выполнены py_compile и git diff --check. CI/push/release не было.

## Следующий шаг

Сравнить синхронные ограниченные замеры до локального Wi-Fi gateway и VPS, собрать
счётчики link/retries и изменения уровня сигнала без записи SSID/BSSID. Если задержки
совпадают уже до роутера, проверить локальный участок; если нет — исследовать внешний
маршрут. ICMP может обрабатываться иначе TCP, поэтому один ping не является доказательством.
До выяснения не менять тайм-ауты или транспорт вслепую и не устанавливать TCP-helper
на ноутбук для длительного теста. Затем короткий host rollout с backup и AWG→TCP recovery.
РКН, неисправность REALITY или конкретный проблемный узел этими данными не установлены.
