# TCP-пилот: контрольная точка 11.09.2026

**VLESS + REALITY работает в коротких проверках, но пока нестабилен. Включать его
в стабильный клиент или считать этап устойчивости завершённым нельзя.**
База разработки — `55e13be`; исходники сохранены отдельно в локальной ветке
`pilot/tcp-reality-2026-09-11`. Основной WG/AWG-код и его ярлык не переключены на эту ветку.
Публикации, push и GitHub CI в этом этапе не было.

## Что реализовано и установлено

- Отдельный серверный Compose-проект `family-connect-tcp`, контейнер
  `family-connect-tcp-gateway-1`, внешний TCP/443 → внутренний TCP/8443.
  Каталог: `185.251.89.19:/opt/apps/family_connect/tcp-pilot`.
- Xray **26.3.27**, commit `d2758a023cd7f4174a5a5fa4ff66e487d4342ba0`, Go 1.26.1.
  Это закреплённая проверяемая версия, не утверждение о последнем upstream release.
  Образ `family-connect-xray:26.3.27-pilot1`, ID
  `sha256:865c9e3311707e87476611c4fd65dc840ef5b4addf7bac5822e08245e59a5453`.
- REALITY target/SNI: `www.cloudflare.com`. Первоначальный `www.microsoft.com`
  проходил обычную TLS 1.3-проверку, но REALITY handshake завершался EOF.
  После смены target/SNI короткие тесты заработали. Похожее наблюдение опубликовано
  в [upstream discussion](https://github.com/XTLS/Xray-core/discussions/6387);
  точная внутренняя причина этого несовпадения не установлена.
- Серверные ключи созданы на сервере. `state-tcp/server.json` и `linux.conf` — 0600,
  каталог 0700, UID/GID 65532 для контейнера. Нет host networking, capabilities сняты,
  root filesystem read-only. Маршрутизация Xray блокирует перечисленные приватные
  диапазоны и TCP/25; выход настроен IPv4. Три прежних WG-пира сохранены.
- Linux helper установлен: `/usr/local/lib/family-connect-tcp/helper`, рядом Xray,
  root-owned `backend.py`, `profile_config.py`, лицензия. Служба
  `/etc/systemd/system/family-connect-tcp@.service` не включена в автозапуск.
  Профиль `fctcp75850269` принадлежит UID 1000, привязан к WG UUID
  `ca453659-ff38-4993-bb04-0d62878d39c4`; парный AWG — `fcawg6c19c559`.
  Закрытый профиль: `/etc/family-connect/tcp/fctcp75850269.conf` (0600).
- Клиентский черновик: строгий JSON-конверт внутри `.conf`, без произвольного Xray JSON,
  shell hooks и путей; цепочка WG → AWG → TCP, остановка предыдущего транспорта,
  проверка внешнего IP через выбранный интерфейс, отмена авторизации прекращает цепочку.
  Изменения находятся в экспериментальной ветке, не в основном ярлыке.
- TUN `10.79.0.2/32`, `fd79:92::2/128`, MTU 1280; policy table/mark 64630,
  priority 10630 для IPv4/IPv6. Mark исключает внешние соединения Xray из TUN.
  DNS через systemd-resolved: 1.1.1.1/9.9.9.9, домен `~.`. Служба очищает свои правила,
  DNS и временный конфиг при остановке; ExecStopPost предусмотрен и для аварийного выхода.
  У закреплённой версии TUN нет новых автоматических routing/DNS опций из текущей
  [веб-документации](https://xtls.github.io/en/config/inbounds/tun.html): это учтено вручную.

Стабильный Linux **0.2.7**, опубликованный desktop **0.2.8**, каталог sequence **7**,
основной product/WG server **0.2.1** и AWG-пилот сохранены. TCP-контейнер остаётся
развёрнутым отдельно, но клиентский тестовый туннель выключен.

## Подтверждённые проверки и незакрытая проблема

- Финальный Python-набор исходников: **222 passed**, в том числе **78 desktop**.
  Два прежних предупреждения FastAPI/Starlette. GTK: **24 layouts**, polling,
  confirmation и recovery regressions прошли; нативный Windows/Android TCP не проверялся.
- Изолированный Docker-клиент: настоящий TUN → REALITY → HTTPS с ожидаемым egress,
  DNS UDP-запрос к 1.1.1.1 внутри VLESS/TCP, заблокированные внутри контейнера
  UDP/51820 и UDP/51821; незарегистрированный VLESS UUID отклонён, рабочий профиль
  после отрицательного теста снова прошёл. Это не имитация полноценного VPN через SOCKS.
- Реальный ноутбук: прямой TCP, HTTPS от обычного пользователя и установка DNS прошли.
  При блокировке обоих UDP-портов реальный backend дошёл до TCP за **16,81 с**.
  Авторизация оператора выдана до измерения, время ввода Polkit-пароля не включено.
  Это один успешный короткий прогон после нескольких неудачных попыток, не гарантия
  устойчивости. Ошибка обработки исключения в тестовом harness была отдельно исправлена.
- Повторные замеры выявили таймауты. Пределы connect/max **3/5 с**: 17 успешных запросов
  из 24, хотя бы один успешный ответ в 9 из 12 пар. При **8/12 с**: 17/24 и 10/12 пар.
  Значит, простое увеличение таймаута проблему не решило; рабочие таймауты кода не изменены.
- Последний замер **8/12 с** с осмотром состояния: 21/24 успешных запросов;
  числовой HTTPS endpoint — 12/12, ipify — 9/12; хотя бы один успех во всех 12 парах.
  Наблюдались DNS, connect и HTTP-response timeout. Адреса TUN и policy rule сохранялись;
  маршрут к 1.1.1.1 шёл через TUN, помеченный маршрут к серверу — через физический интерфейс.
  systemd показывал `active`, NetworkManager — `connected (externally)`.
  Потеря адреса/правила в снятых точках не подтверждена. Счётчики интерфейса не показывали
  errors/dropped. Это не исключает проблем TUN/gVisor, DNS, внешнего канала или REALITY.
- Итоговую очистку подтверждает [машинный отчёт](../tcp-pilot-result.json): служба
  inactive, интерфейс/ownership marker отсутствуют, обе policy rules и тестовые nft tables убраны.

**Причина нестабильности не установлена.** Установившаяся AWG-сессия → автоматическое
восстановление через TCP ещё не проверена вживую. Проверки в российских сетях/DPI,
длительная нагрузка, аварийное завершение, IPv6 leak/egress и полный endpoint loss впереди.
TUN проксирует TCP/UDP, не произвольный IP/ICMP; прозрачность QUIC и IPv6-интернета
не заявляется. Kill switch не реализован. Один сервер/IP не даёт резервирования при
блокировке самого IP. Reticulum-доставка настроек по-прежнему не реализована.

## Как продолжать

1. Взять локальную ветку `pilot/tcp-reality-2026-09-11`; рабочая копия checkpoint —
   `/tmp/fc-tcp-checkpoint`, исходная тестовая копия — `/tmp/fc-tcp-work`.
   Если `/tmp` очищен, исходники восстанавливаются из ветки. Не переключать основной
   ярлык на TCP до устранения нестабильности.
2. Операторские скрипты, бинарник, закрытый профиль и исходные результаты сохранены
   локально в ignored `state-client-build/tcp-checkpoint/`. Скрипты сохраняют исходные
   абсолютные пути `/tmp`; перед повтором восстановить соответствующие файлы или
   отредактировать пути. Deploy-скрипт — первоначальная установка, **не повторять** на
   существующем deployment. Текущий target указан выше, не брать старый Microsoft default.
3. Сравнить длительные проверки через SOCKS и TUN при одинаковом REALITY outbound,
   отдельно DNS по UDP/TCP, числовой HTTPS endpoint и внешние соединения Xray.
   Снять метрики/ошибки ядра без пользовательского payload и ключей; проверить влияние
   системного управления TUN и фонового трафика. Не объявлять причиной NetworkManager
   или DPI без подтверждения. Временное debug-логирование сервера после диагностики выключено.
4. После воспроизводимого исправления повторить длительную серию, оба UDP-block теста,
   явный Disconnect/очистку/аварию и установленную AWG → TCP recovery; затем native
   Windows/Android, CI и подписанный релиз. Наличие локального workflow не означает CI pass.

## Откат

На ноутбуке остановить только `family-connect-tcp@fctcp75850269.service` через systemd;
проверить отсутствие `fctcp75850269`, priority 10630 в IPv4/IPv6 и `/run/family-connect-tcp/active`.
Основной WG/AWG-клиент уже остаётся на прежнем коде; стабильное приложение откатывать не нужно.
Для остановки серверного эксперимента: на разрешённом VPN-хосте в каталоге
`/opt/apps/family_connect/tcp-pilot` выполнить `docker compose -f compose.tcp.yaml down`.
Это отдельный проект; не останавливать соседние проекты и не удалять приватные профили/ключи.
Копии ключей, бинарники, исходные диагностические данные и серверная БД не входят в Git.
