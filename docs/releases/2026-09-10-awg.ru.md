# AmneziaWG: первый этап устойчивости — 10.09.2026

Добавлен AWG 2.0 рядом с существующим WG. Это рабочий пилот Linux, а не опубликованный
кроссплатформенный выпуск. Linux 0.2.7 в `current` и опубликованный каталог 0.2.8
не заменены. Изменения клиента находятся в рабочем дереве на базе 0.2.8; отдельный
ярлык **Family Connect — AWG pilot** запускает их с пометкой AWG pilot.
[Результаты](../awg-resilience-result.json).

## Linux

Helper установлен в `/usr/local/lib/family-connect-awg/`, root-owned; профили в
`/etc/family-connect/awg/`, файлы конфигураций root-only 0600. Метаданные содержат
только публичные ID, endpoint и владельца. Вызовы через `pkexec` требуют стандартного
подтверждения администратора; постоянное беспарольное правило не добавлялось.
Профиль `fcawg6c19c559` связан с WG UUID `ca453659-ff38-4993-bb04-0d62878d39c4`.

Парсер явно разрешает AWG 2 поля, проверяет пределы padding, непересекающиеся диапазоны
заголовков и грамматику signature packets. Hooks, SaveConfig и неизвестные поля
отклоняются. Старый импорт WG/Windows по умолчанию отклоняет AWG-поля.
Системный helper получает текст через stdin, не ключи в аргументах процесса.

При подключении связанного WG-профиля backend выполняет до двух HTTPS-проверок,
привязанных к интерфейсу. Для этого односерверного пилота внешний IP должен совпасть
с IP endpoint. При неудаче WG отключается, затем включается AWG. AWG-helper проверяет
HTTPS egress и свежий handshake, при ошибке убирает туннель. Если ручное включение
AWG прервало уже активный WG и не удалось, backend пытается вернуть WG.
Отключение исходного WG-профиля отключает и его активный AWG fallback.

При установке частной копии awg-quick внесена одна проверяемая правка: не записывать
`src_valid_mark=1` повторно, когда значение уже 1. Это позволяет тестировать full tunnel
в контейнере с read-only `/proc/sys`. Системный wg-quick не меняется.

## Проверки

- Полный Python suite: **189 passed**. Из них 45 Python desktop tests: legacy import, AWG validation/injection rejection,
  bounded fallback, запрет запуска второго туннеля при ошибке отключения первого,
  привязка HTTP probe к интерфейсу, восстановление ранее активного WG при ошибке AWG.
- Upstream engine/local tests прошли. `outline` integration требует внешнего тестового
  VPN и не входит в сборочную проверку; первоначальный полный запуск показал именно
  эту зависимость. Не заявляется, что весь upstream suite прошёл.
- `python -m scripts.test_awg_gateway`: два контейнера в отдельной internal-сети,
  настоящий handshake AWG 2 и HTTP через туннель, без host routes и публичных портов.
- Ноутбук → рабочий AWG gateway: helper install/import/up/down в изолированном
  контейнере, HTTPS/DNS, очистка IPv4/IPv6 routes, имитация блокировки AWG endpoint,
  отказ с очисткой и успешное повторное подключение после снятия блока.
- Реальный Linux host: установлен helper, импортирован профиль, проверен туннель,
  затем отключён. Отдельный тест временно блокировал только WG endpoint UDP/51820
  через собственную nft table. Настоящий backend переключился на AWG за
  **10.7 с**, подтвердил интернет; тестовая таблица и туннели удалены.
  Harness запускался с операторскими правами; интерактивный Polkit в этот тайминг не входит.
- GTK 4.8/libadwaita 1.2: polling/confirmation/state regressions и 24 layout cases.
  Дополнительно прошли 6 layout cases с пометкой AWG pilot.
  Добавлен AWG CI workflow; удалённый GitHub CI для этих незакоммиченных изменений
  ещё не запускался. Windows/Android AWG runtime не реализован и не проверен.

## Ограничения и следующий этап

Автопереход выполняется при нажатии подключения; непрерывный мониторинг обрыва уже
работающего туннеля и автоматическое восстановление в фоне ещё не реализованы.
Проверка одним HTTPS-сервисом может дать отказ при недоступности самого сервиса;
перед массовым rollout нужны несколько независимых сигналов здоровья.
Kill switch и бесшовное сохранение TCP-сессий не заявляются. WG и AWG используют UDP
и тот же VPS/IP: блокировка IP или всего UDP может отрезать оба транспорта.
Испытания в российских операторских сетях ещё нужны.

Далее: bounded background recovery и TCP-транспорт VLESS + REALITY, нативные AWG/TCP
движки Windows/Android; доставка новых настроек через независимые пути Reticulum.
Для реальной проверки смены заблокированного сервера нужен второй разрешённый VPS.

## Rollout и rollback

Пересборка: `docker build -f pilot/awg/Dockerfile -t family-connect-amneziawg:2-pilot1 .`.
Не подменять существующий развёрнутый образ: при изменении содержимого использовать новый тег.
Секретный server.conf подготавливается оператором до `docker compose -f compose.awg.yaml up -d`.
Linux helper: `sudo sh clients/linux/install-awg.sh SOURCE_CHECKOUT BINARY_DIRECTORY`;
бинарные файлы извлекаются из проверенного образа, не из случайной загрузки.

Откат серверного дополнения: из `/opt/apps/family_connect` выполнить только
`docker compose -f compose.awg.yaml down`. Это сохраняет `state-awg`, не меняет WG
и product DB. Никакие старые backups продуктовой БД для этого отката не нужны.
На Linux сначала отключить AWG через helper `down fcawg6c19c559`, затем пользоваться
обычным установленным Family Connect 0.2.7. Не удалять root-профиль активного туннеля.
При отзыве пилотного AWG-доступа отдельно убрать peer из работающего awg0 и server.conf:
продуктовый revoke пока не управляет этим новым transport.
