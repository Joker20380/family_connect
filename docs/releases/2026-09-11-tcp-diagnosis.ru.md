## Что проверено

не совершенно одинаковые ограничения общего времени запроса.

- Длинная серия **без TUN**: 36/36 в каждой из шести категорий — SOCKS numeric,

## Что установлено по трассировке и коду

Записывались только SYN/RST-заголовки TCP для `185.251.89.19:443`, без TLS/HTTP payload.
На физическом интерфейсе — 13972 записи, на TUN — 191. Уточнение после разбора:
на TUN оказались **RST**, а не SYN. Это не доказательство рекурсивного установления
соединений. Пакеты сброса к самому VPN-серверу шли внутрь TUN.

Для 5959 различных исходных IP:port в захвате встречался ответ SYN-ACK;
259 таких endpoint имели несколько SYN. Агрегатор не различает повторное использование
порта по TCP sequence и не доказывает отсутствие потерь или точный процент retransmit.
Сами TCP-соединения во многих случаях устанавливаются; это не постоянная недоступность IP.

В `clients/linux/tcp-helper.py` после системной local table добавляется правило
priority 10630 `not fwmark 64630 lookup 64630`; в таблице 64630 находится default в TUN.
**Перед ним отсутствует lookup main с сохранением более точных маршрутов.**
Поэтому подходящие LAN/Docker/другие connected routes в main не получают приоритета
над TUN default для непомеченного трафика. В установленном `awg-quick` предусмотрено
`lookup main suppress_prefixlength 0`; TCP-помощник этот важный шаг не воспроизвёл.

Кроме того, обход сервера основан только на socket mark. Наблюдаемые RST показывают,
что это не охватывает все управляющие пакеты к серверу. Генерация RST ядром после
закрытия socket — возможное объяснение потери метки, но авторство/метка конкретного
пакета в данном захвате не измерялись. Исправление должно учитывать gateway destination,
а не полагаться исключительно на метку socket.

Это конкретные проблемы схемы маршрутизации. Их вклад в массовые TLS/DNS таймауты
требует проверки после исправления; не объявлять виновными DPI, NetworkManager,
gVisor или определённую версию Xray без дополнительных доказательств.

## Следующий шаг и безопасная точка остановки

1. Исправить порядок policy rules в экспериментальной ветке: сохранить connected/
   more-specific main routes и отдельный обход gateway для управляющих TCP-пакетов.
   Проверять конфликты приоритетов, владение и удаление только собственных правил.
2. Сначала проверить маршрутизацию и очистку в отдельном network namespace:
   LAN/Docker destination, marked/unmarked gateway packets, IPv4/IPv6, отказ процесса.
3. Повторить SOCKS/TUN с одинаковой контролируемой нагрузкой, затем host failover
   и established-session recovery. Только после этого оценивать готовность TCP.

После обращения пользователя новые сетевые прогоны прекращены; выполнялся только
разбор сохранённых заголовков. Проверено: служба inactive, TUN и ownership marker
отсутствуют, IPv4/IPv6 policy rules и тестовые nft tables убраны. Временные SOCKS/HTTP
слушатели и tcpdump завершены штатными finally-блоками. TCP-контейнер сервера оставлен
как отдельный эксперимент. Откат/остановка сервера — в предыдущем отчёте.
