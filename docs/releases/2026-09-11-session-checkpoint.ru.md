Первый capture был incoming-only: ошибку ETH_P_IP исправили на ETH_P_ALL. Во втором:
3916/4766 записей, socket drops0 с обеих сторон; учтены NAT port rewrite/reuse и диапазоны
sequence при GSO/GRO. Пример:1728 байт отправлены на уровне socket capture, сервер получил
1327; оставшиеся401 повторялись до~20s и не видны серверу. Capture до NIC не доказывает
фактическую отправку каждого сегмента в эфир. Конкретное место потери не установлено.

Offload test действительно выполнен пользователем. Отчёт прочитан после случайного
прерывания сеанса: original TSO/GSO=on, during=off, restored=true; независимо проверено
ethtool on/on, активных fc-offload-restore timers нет. Прямые отказы были преимущественно
TCP connect timeouts; TUN — TLS, также были DNS timeouts. Однозначного подтверждения или
опровержения влияния offload нет из-за деградации контрольного пути.
На последующей read-only проверке VPN inactive, три сайта напрямую ответили HTTP200
за~0.17–0.32s. Полный контроль SSH vs sudo→runuser ещё не выполнен.

## Где остановились и что делать дальше

На втором работа приостановлена по просьбе пользователя; последний проверенный VPN status
inactive. Проверки на первом только запланированы. Установленный stable Linux0.2.7,
published desktop0.2.8, TCP0.1.0 и server0.2.1 не перевыпускались. Первый repo-based pilot
на следующем запуске прочитает изменённый backend из main; это отличается от stable launcher.
Серверная конфигурация изменена только добавлением отдельного TCP клиента.

1. На первом read-only проверить сеть/активные профили/версии, сохранить baseline; не
   использовать жёстко заданные интерфейс/IP/profile id второго ноутбука.
2. Сначала сравнить одинаковые запросы SSH/local-user vs sudo→runuser без VPN, сохраняя
   namespace/UID/routes/DNS. Затем согласованный цикл off→on→off с существующим отдельным
   профилем первого, по20 одинаковых запросов и контролем прямого Wi-Fi во включённой фазе.
3. Если control портится только с VPN — исследовать routing/filtering/накопление sockets;
   если control стабилен, продолжить ограниченный paired capture/offload test; если без VPN
   control нестабилен, сначала локализовать внешнюю сеть. Не объявлять произвольное увеличение
   MTU/timeout исправлением.
4. После локализации — повтор на втором ноутбуке, фиксация source/CI, интеграция pending
   bootstrap packaging, доверенная публикация и новый клиентский release.

Reticulum всё ещё без реальной доставки служебных сообщений; второй независимый VPS отсутствует.
