## UI84_BATCHING_EFFECTIVENESS

**VERIFIED in source and installed artifact provenance; invocation/packing efficiency
on a running physical session remains UNKNOWN.** Both preserved endpoint sources
have the same batching policy. Relevant paths below are relative to the retained
client source; the gateway uses its independently inventoried carrier tree.

1. `carrier/wholedevice/session.go:394` passes the concrete secured
   `*familysession.Session` to `tcpforward.NewMux`. Gateway
   `carrier/roombroker/gateway.go:118` does likewise. No wrapper hides its methods.
2. `carrier/tcpforward/mux.go:132` detects `SendBatchContext` by interface assertion;
   it is automatically available for this session. This is not an opt-in flag.
3. `mux_stream.go:218` caps each DATA payload at
   `16362 - 12 - 10 = 16340` bytes when this method is available. Family framing
   is12 bytes/message, Mux framing10, TLS1.3 record overhead normally22.
4. `mux.go:319` takes **currently ready** scheduler frames, at most32 and16362
   plaintext bytes. It does not wait for more traffic to fill a batch. If the next
   frame exceeds the remaining budget it retains that frame for the next pass.
   One queued send head per stream also limits aggregation opportunities.
5. For one frame it calls ordinary `SendContext`; for two or more it calls
   `SendBatchContext`. `familysession/batch.go:17` combines the existing framed
   messages in one TLS Write while preserving each Family sequence number.
6. TLS ciphertext crosses the existing pipe bridge in `familysession/session.go`
   before `ReliableStream.SendContext` assigns DATA sequence/window slots.
   Thus batching is **before Reliable window accounting**, not merely RTP coalescing.
   TLS initial dynamic record sizing can still split a Write; batching is not a
   guarantee of exactly one FRS DATA per call throughout startup.

The async writer in `reliablestream/stream.go` lets receive/consume/ACK processing
continue while a lower send is busy. Its completion is still local endpoint enqueue,
not remote ACK. ACK/open coalescing is not application DATA batching. Neither change
turns each application write into a full16KiB Reliable segment.

**Relation to384B/80ms:** the previous test sent384-byte Reliable payloads directly,
not384-byte application messages through the UI84 Mux batch API. Eight such slots
hold3072B; `3072*8/0.080 = 307200 bit/s`, explaining the synthetic~0.30Mbit/s.
Small application messages additionally carry Mux/Family/TLS framing. It is invalid
to assign that experiment's exact record size to this installed phone.

Existing UI84 can reduce slot waste when multiple messages are already ready and
avoids the oversized full-Mux-write boundary with its16340 cap. It can still send
small singleton records when the scheduler has only one small ready message. Hence
“UI84 has batching” does **not** prove window starvation is impossible; nor does
the direct small-record experiment prove that it occurs in ordinary UI84 downloads.
Earlier synthetic UI84 Mux results already improved over root main; they are not
new measurements and do not select another optimization.

No supported batch enable/disable control exists in the inspected Mux config,
caller paths or native API. Production `NewMux` takes a concrete Family session;
test-only endpoint substitutions are not a runtime switch. Diagnostic socket
environment/drop-ins cannot enable features compiled out of these binaries.
Comparison B is therefore **NOT AVAILABLE**, not permission to edit source/flags.

## RELIABLE_WINDOW_UTILIZATION

Both inventoried sources use `DefaultConfig`: payload16384, send8, receive16,
RTO1s, retries8, max-age20s, maximum window32. `familysession.Open` selects it;
the configured gateway arguments contain no window override. These are verified
implementation defaults; no live negotiated window was available to read.

`send_next - send_base` counts occupied sequence slots. Selective ACKs suppress
retries but do not free slots until cumulative progress; receiver consumption can
delay that progress. Maximum fully packed flight is131072B. At80ms this is a
13.1Mbit/s window envelope, versus0.307Mbit/s for eight384B records. At500ms the
full window permits~2.10Mbit/s; at1s~1.05Mbit/s. These are bounds, not carrier rates.
A0.3Mbit/s full-window flow would require~3.50s feedback/consumption time, unless
another stall dominates. Measure record sizes and feedback together.
