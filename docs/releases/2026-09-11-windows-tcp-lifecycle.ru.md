# Windows TCP: владение процессом и аварийная остановка

Дата: 2026-09-11. Продолжение этапа 4.

Добавлен `clients/windows/TcpEngine.cs` — внутренний механизм владения Xray,
предназначенный для сетевой сессии Windows broker. Публичной IPC-команды запуска
пока нет: включение TCP требует также корректного применения и отката маршрутов/DNS.
Существующий WG connect и GUI не менялись.

Перед запуском проверяются фиксированные SHA256 Xray и Wintun из ранее принятой
Windows-сборки. Файлы удерживаются открытыми без разрешения записи/удаления.
Каталог должен быть доверенным и недоступным для изменения обычному пользователю;
в будущем broker использует фиксированный каталог в Program Files, а не путь из IPC.
Текущий CI использует отдельный каталог runner.temp с теми же проверенными бинарниками.

Создаётся ненаследуемый unnamed Windows Job Object с KILL_ON_JOB_CLOSE.
Xray запускается с `-format json -config stdin:`; фиксированный upstream loader
ждёт EOF. Только после включения процесса в job передаётся конфигурация и закрывается
stdin. При ошибке назначения профиль не передаётся, дочерний процесс завершается.
Профиль не записывается в открытый файл и не помещается в argv/environment.
stdout/stderr дренируются без сохранения потенциальных реквизитов доступа.
Окружение процесса ограничено списком стандартных Windows-переменных, системными
путями и фиксированными Xray directories. Профиль/переменные из IPC не принимаются.

Dispose закрывает job, ждёт завершения процесса и освобождает файловые handles;
повторный Dispose допустим. При аварийной смерти владельца job handle закрывает
Windows и завершает Xray. Это процессная гарантия; восстановление внешних маршрутов
и DNS после смерти будущего broker должно реализовываться отдельно.

Первый CI `34636159620` не получил адаптер. Диагностический CI `34636818841`
показал точную причину: SetupAPI не смог установить Wintun, код0xCB (отсутствующая
переменная окружения). Вdc8df7d сохранены стандартные Windows-переменные, необходимые
первой установке драйвера. Тестовый владелец также теперь отслеживает неожиданное
завершение Xray, не блокируясь чтением консоли. Диагностика движка включается только
символом TCP_ENGINE_TEST в отдельном synthetic CI harness, отсутствующим в приложении.

## Приёмка

CI harness компилирует тот же `TcpEngine.cs`, что и приложение. Три запуска:
обычная остановка, принудительное завершение владельца, принудительное завершение
Xray с последующим Dispose владельца. В каждом — шесть локальных HTTP-запросов через
настоящий Wintun и локальный VLESS. Затем проверяются отсутствие Xray/адаптера и
сохранность основных маршрутов/DNS. Следующий запуск подтверждает повторное создание.
Используется только собственный маршрут `198.18.0.1/32` на одноразовом Windows runner.
Подмена каждого бинарника отдельно должна отвергаться до запуска процесса.

Проверка не использует профиль пользователя, gateway, REALITY handshake или внешний
VPN; не возобновляет отложенные пользователем сетевые/нагрузочные испытания.
Жизненный цикл выполняется CI-владельцем, не LocalSystem broker: его интеграция и
SCM restart/cleanup остаются впереди. Реальный broker DPAPI import проверен ранее.
