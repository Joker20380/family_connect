Приняты два полных цикла подключения и отключения в настоящем GTK-окне paired
preview. Проверка выполнялась программной отправкой сигналов кнопкам приложения,
на пользовательском display, без CI renderer/a11y overrides. Это не ручной UX-тест.

## Результаты и ограничения

В каждом из двух циклов кнопка подключения дала `Tunnel is on`, кнопка проверки IP —
`IP: 186.246.45.246 · NL`; отдельный curl к ipify с привязкой к VPN-интерфейсу
подтвердил `186.246.45.246`. HTTPS-запросы использовали доменные имена.
Кнопка отключения завершила каждый цикл. После закрытия preview IPv4/IPv6 rules,
основные default routes, resolv.conf и список активных соединений совпали с исходными;
pending operation отсутствует. Профиль оставлен неактивным, автоподключение выключено.

Первый сценарий остановился на автоматизации Gtk.FileChooserNative: после set_file
get_file не вернул путь за40с. Импорт не выполнен, состояние сети не изменилось.
Повторный импорт сделан через backend приложения и его обычную async submit boundary.
Это не приёмка пользовательского диалога выбора файла.

Второй сценарий импортировал профиль, но ошибочно переименовал его в
`fc-Amsterdam-pilot`, вне обязательного префикса `fc-app-`. Профиль исчез из списка
приложения; ожидание подключения истекло. Ошибка проверочного сценария исправлена
переименованием существующего профиля, без повторного импорта. Cleanup вернул сеть
к исходному состоянию. Первые два результата сохранены рядом с успешным третьим.

[Машинные результаты трёх запусков](2026-09-13-amsterdam-gui.json).
Полный Python suite не повторялся: код продукта не менялся; предыдущий результат462
описан в отчёте развёртывания. Новая проверка — именно реальный GTK/NetworkManager/HTTPS.
Скриншот не сохранялся; свидетельства UI — значения виджетов и callback results.

## Продолжение и возврат

Обновление установленного приложения, release/catalog и старого шлюза не выполнялись.
Новый сервер в этом шаге не менялся. Удалённый RNS relay пока не развёрнут, импорт WG
не является доставкой подписанной конфигурации через Reticulum. Прежние device identity,
journal и anti-replay floor сохранены; новый Amsterdam WG peer — отдельный ключ.

Следующий шаг: внешний trusted Reticulum relay, постоянная identity и проверенный
public anchor, согласованная регистрация Amsterdam peer и подписанная конфигурация
с корректной возрастающей revision; затем доставка/apply/ACK через внешнюю сеть.
Длительная стабильность, sleep/handover, bare-link toggle и альтернативные транспорты
остаются открыты. Stage5/6 целиком не закрыты.

Откат этого шага: приложение уже закрыто, VPN выключен. При необходимости удалить
только указанный неактивный UUID через NetworkManager; приватные исходные ключи и
control journal сохранять. Прежняя установленная версия не заменялась.
