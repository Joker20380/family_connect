# Добавление VPN-серверов при росте нагрузки — проект решения, 20.09.2026

Это предложение для обсуждения, не описание работающего автоматического масштабирования.
Новые VPS не заказаны; настройки шлюзов и маршрутизация пользователей не менялись.

## Что есть сейчас

Два Friends gateway: RU и NL, оба с AWG 3.1 и TCP REALITY.
`provisioning/friends_catalog.py`, Android ControlFriendsCatalog и Windows FriendsCatalog
принимают ровно два шлюза, по одному на страну. `deploy/friends/access-api.py`
направляет регистрацию по жёстко заданному country → host. Выбора по загрузке нет.
Доступ выдаётся отдельному устройству; публичные шаблоны подписываются офлайн,
личные параметры выдаются через аутентифицированный API.

## Предлагаемый порядок

1. Измерить ёмкость каждого шлюза: полезную пропускную способность, CPU по ядрам,
   потери/задержки, число реально активных устройств, память, ошибки новых подключений,
   лимит месячного трафика провайдера. Собирать агрегаты, без истории посещений.
   Число зарегистрированных профилей не равно нагрузке. Нагрузочные испытания
   ранее отложены пользователем; не возобновлять автоматически.
2. Ввести реестр шлюзов: gateway_id, страна/регион, транспорт, проверенные endpoints,
   измеренная ёмкость, состояние warming/active/draining/offline и свежесть health.
3. Перевести каталог на версию 2 с произвольным списком gateway_id и отдельным
   назначением устройства. Старым клиентам продолжать выдавать совместимый v1;
   нельзя просто добавить третий элемент: нынешние клиенты его отвергнут.
4. Новый VPS проходит установку фиксированных компонентов, проверку исходящего
   интернета/DNS/очистки и ограниченную приёмку. Его публичные параметры подписываются
   офлайн до допуска. Приватные ключи остаются на устройствах/серверах своего назначения;
   действующий offline root не переносится в автоматику.
5. После допуска новые устройства/новые назначения направляются на менее загруженный
   здоровый сервер выбранной страны. Назначение закрепляется за устройством, чтобы
   каждое открытие приложения не перебрасывало его между серверами.
6. Действующие соединения при обычном расширении сохраняются. При drain часть устройств
   получает новое назначение при следующем подключении. Принудительная смена шлюза
   рвёт текущие сетевые сессии; бесшовность не обещается.
7. При аварии — ограниченное восстановление через резервный gateway с проверкой
   интернета и возможностью отката. Нужен независимый вход в служебный канал:
   добавление VPN VPS само по себе не устраняет зависимость от единственного API.

## Когда добавлять

Предварительный ориентир для обсуждения: предупреждение при устойчивых 60–70%
измеренной полезной ёмкости в часы пик, подготовка нового узла заранее, а не при 100%.
Это не измеренные пороги текущих VPS; окончательные значения зависят от наблюдений,
времени подготовки узла и характера трафика. Короткий пик не запускает переносы.
Нужны сглаживание и разные пороги включения/выключения ограничения выдачи.
Для переживания отказа одного узла оставшаяся ёмкость должна выдерживать его трафик
(N+1); просто держать каждый сервер ниже 70% недостаточно для любой топологии.

## Безопасное назначение и эксплуатация

Назначение создаётся транзакционно с резервированием ёмкости и лимитом конкурентных
выдач. Устаревшие метрики исключают новые назначения. Номер версии/эпоха назначения
защищает от отката на устаревший endpoint; gateway_id, адрес, транспорт и устройство
проверяются как связанный набор. Регистрация peer на новом сервере подтверждается
до выдачи успешного результата клиенту; при частичном сбое нужна сверка и откат.
Выдачу и отзыв доступа синхронизировать со всеми узлами, где есть peer устройства.
Подсети и выдача адресов должны быть явными для каждого gateway, без коллизий.

Первый этап — оператор добавляет заранее проверенный сервер, система распределяет
новые назначения. Заказ/удаление VPS через API провайдера — отдельная последующая
задача с бюджетными лимитами и явным разрешением владельца.

## Оставшиеся решения

- Измерить текущую нагрузку и определить желаемый запас/допустимую скорость на пользователя.
- Приоритет регионов и допустимость резервного выхода через другую страну.
- Согласовать каталог v2 и обновление трёх клиентов до включения нового шлюза.
- Принять независимую доставку конфигураций и сквозную аварийную смену (этапы 5–6).
