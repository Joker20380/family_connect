## Результат для оператора

Оператор использует единый штатный процесс в панели с ограниченным исполнителем.
Он задаёт подготовленный сервер, публичный адрес, защищённый профиль доступа и роли;
локация, ёмкость и версия пакета имеют проверенные значения по умолчанию либо явно
выбираются до запуска. Система формирует план, выполняет установку и регистрацию,
проверяет реальные соединения, публикует узел и показывает итог с причиной любого отказа.
Согласованный CLI может использовать тот же процесс для автоматизации и восстановления.

«Указать доступ» означает выбрать credential reference, локальный SSH agent или другой
принятый защищённый способ подключения. Веб-панель не получает приватный SSH-ключ,
root signing key или произвольную shell-команду. Исполнитель имеет ограниченные
полномочия и проверяет host-key, целевой сервер, роли и точную версию пакета.

Доступ и полномочия проверяются до старта. Если нужна подпись офлайн-владельца,
система заранее готовит конкретный допуск на сервер/роли/пакет; действительное разрешение
не запрашивается повторно на каждом шаге. Отсутствие технического доступа или обязательной
подписи отображается как конкретный блокер. Ключ подписи не переносится в веб-приложение
или на новый gateway ради автоматизации.

Подготовка и оплата VPS остаются у оператора: интеграция с покупкой серверов у провайдера
не требуется этим контрактом. Поддерживаемая матрица ОС/архитектуры указывается явно;
«любой новый IP» не означает поддержку произвольной ОС, транспорта или протокола.

## Роли и идентичность

- `gateway_id` обозначает логический шлюз; каждый физический VPS получает отдельный
  `instance_id` и собственную identity. Новый экземпляр не копирует приватный ключ старого.
- VPN gateway устанавливает выбранные транспорты, локальное применение допуска и
  мониторинг. Он получает только необходимые ему полномочия и данные.
- Управляющий API подключается к принятому состоянию кластера и discovery. Добавление
  API или VPN gateway само по себе не меняет состав голосующих участников.
- PostgreSQL replica и участник etcd вводятся отдельными явно выбранными membership
  операциями с проверкой синхронизации, кворума и независимости отказов.

Точный набор ролей, подписей и prerequisites показывается до запуска. Необъявленные
роли и незавершённый транспорт не скрываются под общим статусом «узел готов».

## Критерии приёмки

| ID | Обязательный результат | Как подтвердить |
| --- | --- | --- |
| ONB-01 | Повторяемый ввод через панель/исполнитель и общий CLI | Чистый VPS поддерживаемой платформы, новый ID и публичный IP вводятся без изменения исходников, hardcoded списков и индивидуальной сборки installer. Панель запускает реальную операцию и получает её результат. |
| ONB-02 | Логическая и физическая идентичности разделены | Добавить новый gateway, затем заменить физический экземпляр существующего; сохранить логический ID, выдать новую identity и исключить неразрешённую одновременную активность старого и нового экземпляров. |
| ONB-03 | Рабочая регистрация и выдача полномочий | Одноразовый допуск связан с экземпляром, ролями и пакетом; проверено владение ключом. Replay, подмена роли/узла и rehearsal credentials отвергаются. Действует production цепочка доверия и последующее обновление полномочий. |
| ONB-04 | Проверенная установка только выбранных ролей | До изменений проверены ОС/архитектура, адрес, SSH trust, ресурсы и порты. Подписанные артефакты воспроизводимы; чужие службы и правила сети сохраняются. Несовместимый сервер получает ясный отказ. |
| ONB-05 | Реальная внешняя готовность | Для каждого выбранного VPN-транспорта выполнены соединение, DNS/HTTPS и ожидаемый выходной адрес; для API — аутентифицированная операция с актуальным состоянием. Проверочная identity ограничена, ресурсы убраны; один local health не достаточен. |
| ONB-06 | Успех означает полный допуск и публикацию | Зарегистрированная identity, проверенный runtime, внешняя приёмка, применение текущих правил и согласованная публикация подтверждены до итогового ACTIVE. Незавершённая публикация и UNKNOWN видны отдельно; новым пользователям не назначается неподготовленный узел. |
| ONB-07 | Динамический реестр и состав обслуживающих узлов | Новый допустимый ID, новая локация и дополнительный узел в существующей стране проходят общий путь данных. Fencing, revoke, paid-policy, epochs, обязательные ACK и адресные пулы сохраняются при изменении serving set; узел нельзя исключить ради обхода отказа. |
| ONB-08 | Совместимые клиенты получают узел без новой сборки | Подписанный версионированный каталог/discovery доставляет новый адрес и роли. Клиент проверяет подпись, срок и монотонность, сохраняет identity и подключается. Одна миграция на динамический протокол допустима; сборка на каждый последующий сервер — нет. |
| ONB-09 | Прерывание и повтор безопасны | Повтор того же operation ID с теми же параметрами возвращает результат либо продолжает проверенное состояние без дублирования identity/выдачи/публикации. Проверены потеря SSH/ответа, смерть installer и конкурентный запуск до и после commit; UNKNOWN сначала сверяется. |
| ONB-10 | Возврат сохраняет подтверждённые данные | Неудачный кандидат до публикации не принимает пользователей. После публикации отзыв/вывод проходит через новое состояние и применимый drain. Возврат кода не откатывает registry, платежи, отзывы, epochs и replay floors к старому backup. |
| ONB-11 | Существующий сервис и секреты сохранены | Ввод не перемещает здоровые действующие подключения и не останавливает чужие службы. Capacity проверяется перед назначением. Приватные ключи/tokens отсутствуют в Git, CI, argv, логах, веб-ответах; панель хранит безопасные ссылки и receipts. |
| ONB-12 | Роли управляющего кластера вводятся отдельно | Обычный gateway/API не меняет кворум. Для выбранной replica/voter роли проверены catch-up, членство, сохранённое большинство, отказ/возврат. После завершения HA ввод работает при недоступном одном управляющем сервере и сохранённом кворуме, включая отсутствие RU. |

## Сквозная приёмка

На чистом VPS из поддерживаемой матрицы ввести логический ID, который отсутствовал
в известных клиентских списках и коде, с новым публичным IP. Установленный совместимый
клиент должен получить этот узел штатным способом, подключиться и выйти через ожидаемый
адрес. Проверить применимость допуска/отзыва и каждый заявленный транспорт.

Повторить точную операцию; проверить прерывание и восстановление; заменить физический
экземпляр/IP; затем вывести исходный экземпляр. Здоровые остальные узлы и их текущие
подключения сохраняются. Реестр и контроль доступа не редактируются вручную для обхода
сценария. Новый клиентский релиз ради этих адресов не выпускается.

Для управляющих ролей провести отдельную приёмку membership и discovery.
Испытание при недоступном управляющем сервере выполняется в изолированном контуре
либо в заранее ограниченном рабочем сценарии; общий API не отключается всем пользователям
ради демонстрации. Наличие кворума и корректность текущего лидера остаются обязательными.

Приёмочный отчёт содержит точные source/package/client versions, роли, исходное состояние,
проверки допуска/публикации/трафика, состояние после прерывания и возврата. Секреты и
персональные данные хранятся отдельно. Непроверенная роль явно остаётся NOT_RUN.

## Место в текущем плане

Текущая выбранная реализация остаётся **CONTROL-HA-20261123 / HA-02** с четырьмя ранее
зафиксированными результатами. Это требование не создаёт дополнительный подпункт HA-02
и не возобновляет уже закрытые проверки receiver/collectors/support.

Дальнейшая реализация связывает существующий fleet bootstrap с production enrollment,
ограниченным исполнителем панели, динамическим реестром/serving set, подписанным каталогом
и клиентской совместимостью. HA-03 обеспечивает полномочия координатора/receivers,
HA-04 — API/discovery и клиентов, HA-05 — рабочий перенос и аварийную приёмку.
Эти зависимости отражаются в общей очереди; закрытие HA-01..05 не заменяет ONB-01..12.

На принятом исходном checkpoint имеются испытанный disposable bootstrap, регистрация
test/rehearsal identity, внешние проверки AWG/TCP/MESH, reboot и rollback. Панель пока
хранит intents/receipts; production publication/issuance и произвольный клиентский список
не принимаются по этим прежним результатам. Исторические отчёты сохраняют свой scope.

**Модернизация в части ввода новых узлов завершена только после сквозного PASS
применимых ONB-01..12. REQUIREMENT_ACCEPTED не является IMPLEMENTED или DEPLOYED.**
