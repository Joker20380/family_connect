# Архитектура и границы доверия

[English](architecture.en.md) · [Руководство](../README.ru.md)

## Структура сессии

```text
Клиент с генерируемыми тестовыми данными
  → внутренний QUIC + mTLS, сертификат gateway закреплён подписанным каталогом
  → локальный UDP-адаптер
  → внешний QUIC + mTLS к relay A или relay B
  → UDP-соединение relay к выбранному оператором gateway
  → тестовый сервис управляемого gateway
```

Relay расшифровывает только свой внешний участок. Внутренние данные клиент—gateway остаются
зашифрованными. Relay видит адреса соседей, время, объём и адрес gateway, но не получает URL,
историю DNS или конечное назначение приложений. У тестового gateway нет операции произвольного
выхода в интернет. Production gateway неизбежно будет видеть часть метаданных назначения;
анонимность при сговоре gateway/relay или корреляции трафика не заявляется.

## Ключи и допуск

У каждой роли отдельный приватный ключ P-256 и сертификат CA. Постоянная identity — SHA-256
от DER SubjectPublicKeyInfo; она не зависит от IP. Подписанный каталог связывает identity,
отпечаток текущего сертификата и адрес. При сохранении ключа ротация сертификата может сохранить
identity, но автоматическая ротация пока не реализована.

`scripts/identity.py` создаёт приватный ключ и публичный CSR локально. Issuer проверяет подпись
CSR и подписывает его публичный ключ. В тесте на одном хосте отдельные каталоги ролей имитируют
отдельные устройства; администратор хоста имеет к ним доступ. Это не аппаратное хранение
мобильных ключей. Приватный ключ не передаётся по протоколу регистрации/control plane.

TLS требует сертификат устройства с назначением client-auth. После handshake relay/gateway
проверяет членство до создания UDP-соединения relay или выдачи прикладных данных. Серверный
сертификат не заменяет сертификат устройства: этому препятствуют EKU и проверка членства.
Клиент проверяет цепочку CA, имя сервера и подписанный отпечаток. Прикладные данные 0-RTT
отключены. Шифрование, аутентификация пакетов и защита от replay выполняются стандартным
QUIC/TLS; собственного криптоалгоритма и повторно используемого открытого токена нет.

## Подписанное обнаружение

Control API подписывает точные байты JSON через Ed25519 с разделителем домена
`family-connect/network-state/v1\0`. Envelope содержит base64 payload и signature; версия схемы
payload — 2. Версия домена намеренно остаётся 1 для совместимости формата envelope.
Rust отклоняет неверные подписи, истёкшие/будущие сроки, неизвестную схему, дубли identity,
неверные роли, multicast/неопределённые адреса и объявление relay как Internet exit.

Корень доверия устанавливается вне discovery. `/v1/trust-root` помогает при подготовке, но не
реализует trust-on-first-use. Корректная подпись разрешает адреса сети, объявленные оператором;
компрометация ключа подписи остаётся критической угрозой. Для production нужны ограничения
egress на уровне ОС, offline root/intermediate и ротация подписывающих ключей.

Rust пробует настроенные bootstrap URL, затем использует действительный кэш при недоступности
источников. Подписанный файл кэша сохраняет максимальные epoch/время выпуска между запусками.
Обновления используют атомарный rename и fsync. Смена членства требует увеличения epoch;
более старое время выпуска при том же epoch отклоняется. Истёкший корректно подписанный кэш
сохраняет защиту от отката, но не право подключения. Удаление доверенного локального состояния
сбрасывает этот минимум: защита файловой системы устройства входит в модель угроз.

Закрытый каталог стенда содержит отпечатки устройств. Это не окончательная модель публичного
каталога с защитой приватности. До публичной сети нужно разделить топологию и персональные
разрешения устройств и определить минимальный срок хранения телеметрии.

## Отзыв и автономная работа

Локальная CLI оператора меняет членство под файловой блокировкой, увеличивает epoch и атомарно
заменяет файл. Публичного административного HTTP endpoint нет. Узлы опрашивают backend раз
в пять секунд, с таймаутом три секунды на bootstrap URL, и проверяют сессии раз в секунду.
Это измеряемая цель, а не жёсткая гарантия реального времени. Неверное/недоступное обновление
не заменяет уже проверенный действительный кэш.

Удаление узла/устройства закрывает активные сессии после получения нового состояния.
Полная недоступность control plane задерживает отзыв до истечения последнего подписанного
разрешения. Затем и новые, и существующие сессии закрываются. Бессрочная автономная работа
несовместима с немедленным глобальным отзывом; здесь выбран ограниченный срок, обычно 900 секунд.

## Non-exit и эксплуатационные ограничения

Relay принимает непрозрачные внутренние датаграммы, а не команды назначения. Настроенное имя
gateway должно соответствовать роли gateway в подписанном состоянии; смена адреса или identity
завершает существующую relay-сессию. Ответы принимает только UDP-сокет, подключённый к этому
gateway. Клиент дополнительно аутентифицирует сам внутренний gateway, поэтому relay не может
выдать себя за него.

Core-контейнеры работают без привилегий, с read-only ФС, удалёнными capabilities и отдельными
mounts для ролей. Сеть данных — Docker internal. У control API отдельная management-сеть
и порт на localhost хоста. Relay не получает ключ gateway или ключ подписи control plane.

На узел допускается максимум 64 одновременных handshake/сессии, handshake ограничен пятью
секундами. Лимиты байтов relay грубые и задаются на сессию. Это не production DDoS-защита,
справедливое распределение по устройствам, месячные квоты или независимый аудит безопасности.

Смена gateway по-прежнему разрушает внутреннюю сессию. Для сохранения публичных TCP/NAT-потоков
нужны отдельная архитектура egress anchor/состояния и испытания. Переключение relay этого не доказывает.

[проверка клиентов rustls](https://docs.rs/rustls/latest/rustls/server/struct.WebPkiClientVerifier.html),
[соединения и датаграммы Quinn](https://docs.rs/quinn/latest/quinn/struct.Connection.html).
