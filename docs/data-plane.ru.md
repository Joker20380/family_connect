# Реальный IP-трафик через адаптивный контур

[English](data-plane.en.md) · [Руководство](../README.ru.md)

## Что реализовано

Отдельный Linux-стенд `family-connect-data` соединяет настоящий сетевой интерфейс WireGuard
с аутентифицированным контуром relay. Приложения используют обычный TCP/UDP и системный DNS.

```text
curl / DNS / Linux IP stack
    ↓ fcwg0 (kernel WireGuard)
локальный UDP-мост
    ↓ один внутренний mTLS QUIC stream
    ↓ сменяемый внешний mTLS QUIC relay A / relay B
управляемый gateway: QUIC → локальный WireGuard
    ↓ fcwg0 → firewall → NAT
публичный IPv4-интернет
```

Внутреннее QUIC-соединение и UDP-сокет на gateway сохраняются при смене relay. Поэтому
WireGuard peer, адрес внутри VPN и NAT-состояние внешнего TCP-соединения не меняются.
Это проверяет отказ relay при сохранении того же gateway; отказ самого gateway пока не решён.

Reticulum не подключён. Используются ранее реализованные identity, подписанный каталог,
проверка членства и сроков, закрепление сертификатов и автоматическое переключение пути.

## Границы протокола и безопасности

- Новый режим `packet-client` доступен только после внутренней и внешней mTLS-аутентификации.
- Gateway включает операцию пакетов только при `ENABLE_PACKET_GATEWAY=1` и разрешении
  `internet_exit` в подписанном объявлении. Обычный стенд эту операцию не включает.
- Gateway передаёт пакеты только локальному WireGuard на `127.0.0.1:51820`.
  Клиент не передаёт адрес назначения в команду моста.
- Relay-код по-прежнему отправляет зашифрованные пакеты только объявленному gateway.
  У relay нет API CONNECT/SOCKS/NAT; его Docker-сеть не предоставляет публичного выхода.
- Формат внутри stream: двухбайтовая длина big-endian и один зашифрованный WireGuard-пакет.
  Допускается 1–2048 байт; пустые, слишком большие и оборванные кадры отклоняются.
  Чтение кадров не отменяется при поступлении UDP, чтобы не терять границы сообщений.
- Расшифровка IP-пакетов, фильтрация и NAT выполняются только в управляемом gateway.
  Запрещены TCP/25 и выход к частным/служебным IPv4-диапазонам.
- IPv6 направлен в VPN, но его выход отключён. В контейнере клиента нет обычного публичного
  маршрута; при потере обоих relay доступ закрывается. Это не настройка kill switch вашего ноутбука.
- История сайтов, DNS и содержимое пакетов не журналируются. Тест сохраняет метаданные
  специально запрошенной тестовой загрузки, а не пользовательский трафик.

Здесь WireGuard-пакеты идут через надёжный упорядоченный stream. Это позволяет проверить
реальную маршрутизацию без собственного алгоритма фрагментации. Такой режим имеет накладные
расходы и задержку последующих пакетов при потере предыдущего; его нельзя считать оптимальным
транспортом для звонков. Следующий инженерный этап — измерить потери/задержки и выбрать
пакетный транспорт с проверенным MTU. Криптографические алгоритмы не изменяются.

## Развёртывание

Нужны Linux с поддержкой WireGuard, Docker Compose и Python 3. Из корня репозитория:

```sh
docker compose -f compose.data.yaml build
sudo ./scripts/provision_data.sh
python3 scripts/test_data.py
```

Стенд использует `state-v3/`, подсеть `172.29.93.0/24` и API `127.0.0.1:18081`.
Публичные UDP-порты не публикуются. Все тестовые identity и WireGuard-ключи создаются
в отдельных каталогах на одном операторском сервере. Это лабораторные ключи, а не ключи
телефона/ноутбука пользователя. `state-v3/` исключён из Git и Docker build context.

Вспомогательные контейнеры WireGuard имеют NET_ADMIN только в сетевых пространствах
клиента и gateway. Rust-процессы работают без capabilities. Relay не получает NET_ADMIN.
При пересоздании core необходимо пересоздавать и соответствующий WireGuard-контейнер:
они совместно используют сетевое пространство. Скрипт испытаний делает это автоматически.

## Приёмка

`test_data.py` выполняет одну HTTPS-загрузку 8 MiB с публичного сервиса Cloudflare,
без retry/resume. После получения части файла он убивает relay A и проверяет:

1. Загрузка завершается с HTTP 200, ожидаемым размером и одним HTTPS-соединением.
2. Внутренняя QUIC-сессия создана один раз, произошло переключение relay.
3. Внешний IPv4 — `185.251.89.19`; DNS работает через VPN.
4. Публичный IPv6 недоступен.
5. После отключения обоих relay новое публичное соединение не устанавливается.

Сохраняется наблюдаемая SHA-256 загрузки; это не сравнение с заранее известным хешем
публичного файла. Подлинность сервера и целостность передачи проверяет HTTPS.
Тест зависит от доступности публичного тестового сервиса и рассчитан на этот российский сервер.

Результаты: `artifacts/data3/`. После испытания клиент останавливается, инфраструктура стенда
восстанавливается. Прямой VPN `family-connect-pilot` и прежний стенд `family-connect` не меняются.

Это пока один Docker-хост и внешний HTTPS-сервис. Переходы Wi-Fi/LTE, Android TUN,
международные relay, восстановление исчезнувших путей, смена gateway и производительность
в реальных сетях не доказаны. Пользовательские Android/Linux-профили пока остаются прямыми.

## Подтверждённый результат

9 сентября 2026 года финальная версия передала 8 MiB по HTTPS за 28,99 с при заданном
ограничении загрузки 256 KiB/s. Relay A был отключён после получения 708 608 байт.
Сохранились одно HTTPS-соединение и одна внутренняя QUIC-сессия; выполнено одно переключение
relay. Выход — `185.251.89.19`, RU. После отключения обоих relay проверки по имени и прямому
IP завершились отказом. Посторонний сертификат отклонён; 4 Rust- и 6 Python-тестов прошли.
Это результат функционального испытания, а не замер предельной скорости.
