# Fleet5.2: WG/AWG backend и управление через SSH

Состояние24.09.2026: реализовано в исходниках; изолированная native-приёмка
WG/AWG+SSH пройдена, см. [новый отчёт](releases/2026-09-24-fleet-native.ru.md). На рабочие
серверы не установлено. Это продолжение [fencing](fleet-gateway-fencing.ru.md),
а не завершение5.2 или независимого клиентского служебного канала.

## Применение операции

`control/fleet_wg.py` реализует `WGPeerBackend` и диспетчер `WGBackends` для
WireGuard1, AmneziaWG2.0/3.1. Оператор закрепляет абсолютный путь CLI, интерфейс,
публичный серверный ключ и listen-port. Версия CLI/engine должна соответствовать
выбранному транспорту; определение версии по факту запуска ещё не реализовано.

Перед первым intent backend читает только `show <interface> public-key`,
`listen-port`, `allowed-ips`. Наличие такого же клиентского ключа, даже с тем же
адресом, запрещает автоматическое присвоение unmanaged peer. Пересечение адреса
с маршрутом другого peer также запрещает операцию. Импорт старых выдач требует
отдельной процедуры; нельзя включать этот allocator поверх действующего Friends.

После preflight журнал сохраняет intent, затем backend выполняет только
`set <interface> peer <public-key> allowed-ips <IPv4/32>` либо `... remove`.
Повтор pending intent пропускает проверку первого присвоения: peer мог появиться
до падения процесса. Это безопасно лишь при единственном владельце изменений.
После операции повторно читаются peers и pin: проверяется целевой результат и
неизменность маршрутов остальных peers. Нулевой exit-code сам по себе не даёт ready.
Чужая изменённая привязка блокирует и удаление: её нельзя молча перезаписать.

Приватные ключи и `show ... dump` не читаются. Конфиг целиком не переписывается,
маршруты/firewall/engine не перезапускаются. CLI наследует effects-lock из
FencedGateway, поэтому переживший родителя процесс не пересекается со следующим
эффектом. Все остальные writers обязаны использовать ту же блокировку либо быть
отключены для выделенного интерфейса. Проверка после операции не заменяет это условие.

## Ограниченный вызов и канал управления

`control/fleet_process.py`: argv без shell, ограниченный stdin/stdout, stderr
подавлен, timeout, завершение и ожидание прямого дочернего процесса при ошибке.
WG preflight и ensure ограничены каждый10с, вывод каждого CLI —4MiB;
SSH-вызов25с, запрос/ответ до4096байт. Это границы отдельной операции;
массовый recovery ещё требует отдельного ограничения очереди/времени.

`control/fleet_ssh.py`: `SSHGateway` подключается к проверенному публичному IP.
Закреплённый `known_hosts` и отдельный ключ должны быть обычными файлами0600,
принадлежать процессу и не быть symlink/hardlink. Каталог секретов должен быть
доступен для записи только оператору сервиса. Host key доставляется и проверяется
отдельно: слепой `ssh-keyscan` не является проверкой доверия.

SSH игнорирует пользовательский config, требует StrictHostKeyChecking,
отключает agent/password/interactive auth, forwarding, proxy и multiplexing.
Единственная удалённая команда — литерал `fleet-v1`; JSON передаётся через stdin.
Дубли JSON-полей, неверный тип generation и receipt, не совпавший с командой,
отклоняются. При потере ответа worker повторяет исходную идемпотентную операцию.

## Агент и условия будущей установки

`scripts/fleet_agent.py` предназначен для root-owned forced-command установки.
Удалённый вызов без аргументов допускается только с
`SSH_ORIGINAL_COMMAND=fleet-v1`. Локальные `--initialize` и `--recover`
запрещены при наличии SSH_CONNECTION. Агент требует root и umask077.

Фиксированный конфиг `/etc/family-connect/fleet-agent.json` содержит:

- `schema_version: 1`, полный объект `gateway` из принятого реестра;
- абсолютный `state_directory` для приватного gateway journal;
- `bindings`: transport, version, абсолютный binary, interface,
  server_public, port для каждой WG/AWG capability реестра.

Конфиг0600, root-owned, без symlink/hardlink, до64KiB. Конфиг, CLI и родитель
state directory проверяются вместе с родительскими каталогами: root-owned,
без group/world-write и symlink. Код агента, Python/venv и все импортируемые
модули тоже должны быть root-owned и недоступны сервисному пользователю для записи;
эта установка не автоматизирована. CLI через symlink нужно закреплять реальным путём.

SSH-пользователь по умолчанию `fc-fleet` сам по себе не получает root. При будущей
установке требуется проверенный root-owned wrapper с повышением прав строго для
агента, без пользовательских аргументов и произвольного окружения, либо отдельный
ограниченный root key с forced command. Авторизованный ключ должен запрещать shell,
PTY и forwarding; доступ ограничивается IP контроллера. Не выдавать общий sudo.
Политика sshd/ключа, wrapper и systemd unit ещё не подготовлены и не приняты на сервере.

Первый запуск журнала — явный локальный initialize. При рестарте порядок:
поднять engine → локальный recover → проверить peers/трафик → разрешить admission.
Агент не создаёт отсутствующий журнал автоматически. Remote ответ содержит только
receipt либо фиксированную ошибку; секретные traceback не отправляются клиенту.

## Что остаётся до включения

1. Изолированная native-проверка WG/AWG и реального SSH forced command пройдена:
   неправильный host key, запрещённые команды, restart и потеря результата после
   peer effect проверены. Перед production нужна проверка отдельного контроллера/
   межсерверной сети и установленной политики SSH/recovery services.
2. Установка доверенных binaries/config/служб; единственный writer и явная миграция
   существующих выдач. Проверка реального трафика, а не только наличия peer.
3. Интеграция общей авторизации, bounded scheduler и signed publish после ready.
4. Независимый TTL/revoke на gateway при недоступном контроллере, TCP backend,
   мониторинг/recovery без ручного запуска. Сейчас expiry инициирует контроллер;
   отсутствие связи с ним не гарантирует своевременное удаление истёкшего peer.

## Приёмка и откат

[Первоначальный отчёт и163 теста](releases/2026-09-24-fleet-wg-ssh.ru.md). CLI в unit-тестах — отдельный
исполняемый fixture с имитацией интерфейса; это не native VPN и не VPN-трафик.
SSH argv/receipt в unit-тестах проверены подменой runner. Дополнительно выполнены
[12 native-сценариев](releases/2026-09-24-fleet-native.ru.md) с настоящими CLI/engine,
VPN-трафиком и SSH-сервером в изолированных контейнерах; границы приведены в отчёте.
На этом checkpoint откат сервера не требуется: установка не выполнялась.
После будущего включения остановить новые назначения, подтвердить удаления и сохранить
central store и gateway journal. Удаление журнала или запуск старого allocator поверх
занятых IP не являются допустимым откатом.
