# Этап 5: служебный канал и расширяемый парк серверов

Контракт от 24.09.2026, после аудита исходников и уточнения пользователя о новых
серверах, распределении нагрузки и IP-адресах. Это целевая архитектура; фактически
готовые части перечислены в [отчёте](releases/2026-09-24-stage5-audit.ru.md).

## Что должно получиться

Устройство с действующим доступом получает адресно зашифрованную, подписанную
конфигурацию при недоступных основном HTTPS API и VPN. Добавление шлюза или смена
его внешнего IP не требует новой сборки клиента. В одной стране может быть несколько
узлов. Страна — пользовательский фильтр, `gateway_id` — постоянная идентичность узла;
они не взаимозаменяемы. Уже существующие device identity и WG keys сохраняются.

Распределение новых подключений входит в расширенный этап 5. Автоматическое создание
VPS и покупка адресов не входят. Перенос работающего подключения при полном отказе
gateway и сквозная автоматическая смена выхода остаются приёмкой этапа 6.

## Независимый вход

Первый ingress — существующий Reticulum на `186.246.45.246:4242`, основной API —
`185.251.89.19:8443`. Используем имеющиеся VPS. На клиенте заранее сохранены адрес
ingress, public identity Reticulum и отдельный доверенный signing anchor.
Отказ API не должен вынуждать повторную регистрацию или загрузку bootstrap с API.

Android использует сокет, привязанный к non-VPN Network; Linux — ограниченный
root-pinned route lease; Windows должен получить broker-owned эквивалент. Сетевые
запросы не удерживают блокировку изменения VPN. Отказ carrier не выключает здоровый
туннель; ACK остаётся в durable outbox до доставки.

Это независимость от российского API и VPN, но не от отказа всего Амстердамского
хоста. Реестр содержит список ingress и failure domains; второй ingress добавляется
с перекрытием старых и новых pin/address. Различные IP одного хоста не считаются
независимыми узлами. Полную отказоустойчивость нельзя заявлять при одном ingress.

## Реестр серверов

Серверная модель: [`control/fleet.py`](../control/fleet.py). Это доверенный операторский
вход, **не новый формат доверия клиента** и не файл для прямой загрузки клиентом.

| Поле | Назначение |
| --- | --- |
| `revision` | Монотонная версия инвентаря; после изменения endpoints старые метрики не годятся |
| `gateway_id`, `failure_domain` | Постоянный ID и общий домен отказа хоста |
| `country` | Фильтр выбора; число узлов страны не ограничено двумя |
| `endpoints` | Публичный канонический IPv4/IPv6, порт, транспорт и его версия |
| `state` | provisioning → active → draining → disabled |
| `tunnel_pool` | Уникальная RFC1918 IPv4-подсеть; пересечения запрещены |
| `max_devices` | Лимит зарезервированных/выданных мест, не число свежих handshakes |
| `egress_budget_mbps`, `weight` | Утверждённый оператором бюджет и относительная доля узла |
| `control_ingresses` | Адреса, порты, public identity и failure domain служебных входов |

IP внешнего endpoint и внутренний адрес устройства — разные сущности. Запись внешнего
IP в реестр не назначает его сетевому интерфейсу VPS: сначала проверяется владение
адресом у провайдера, настройка интерфейса/маршрута, firewall и реальная доступность.
IPv6 принимается инвентарём, но выдаётся планировщиком только при явно переданной
поддержке клиента; это не утверждение готовности всех нынешних VPN-клиентов к IPv6.

Реестр не содержит приватных ключей и credentials. Неизвестные поля, duplicate JSON,
повторяющиеся sockets/ID, неподходящие адреса, пересекающиеся пулы и невозможная
ёмкость отвергаются. Проверка обновления запрещает уменьшение revision, удаление
постоянного ID, незаметную замену пула/failure domain и замену всех bootstrap-входов
одним действием. Отключённые записи сохраняются; миграция пула требует отдельной
операции над leases. Модель сама по себе не является durable revision store.

Проверка подготовленного оператором JSON:

```sh
python -m scripts.check_fleet /private/fleet.next.json --previous /private/fleet.current.json
```

Команда только проверяет и выводит revision/число узлов. Она ничего не публикует.

## Распределение нагрузки

Планировщик получает аутентифицированные наблюдения с gateway ID и revision реестра:
готовность транспорта, CPU, память, исходящую скорость и количество выделенных мест.
Публичный `/status/server-load.json` предназначен для интерфейса; его данные не
дают разрешения менять маршруты и не заменяют проверку здоровья data plane.
Настроенные сейчас 200 Mbps с пометкой provider-default-estimate нельзя молча
превращать в гарантированную ёмкость при admission.

Для нового назначения исключаются provisioning/draining/disabled, несовместимые
транспорты и семейства адресов, заполненные узлы, отсутствующие или старше 45 секунд
метрики, неверная revision и нагрузка CPU/RAM/egress от 85%. Оставшийся запас и
операторский weight задают долю узла; детерминированное хеширование device+gateway
распределяет устройства без выбора первого сервера для всех запросов.

Уже назначенный здоровый узел сохраняется даже в draining или при выросшей нагрузке.
Пустой результат планировщика — отсутствие безопасного нового назначения,
**не команда остановить рабочий VPN**. Решение не должно обходить ручной выбор страны.
Расчёт при одинаковом snapshot детерминирован; новые метрики могут менять порядок
кандидатов для новых назначений. Фактический выбор требует атомарного резервирования.

## Резервирование адресов, применение и публикация

Локальный слой хранения и резервирования реализован24.09:
[FleetStore: API, ограничения и recovery](fleet-leases.ru.md). Он ещё не связан с
рабочей авторизацией, gateway adapter и подписанной публикацией. Полная цепочка:

1. Одна транзакция проверяет entitlement/revoke, фиксирует gateway и резервирует
   свободный `/32` и место. Уникальны `(gateway_id, address)` и идемпотентный запрос.
   Одновременные запросы не могут превысить max_devices или выдать одинаковый адрес.
2. Durable reconciliation ставит peer/credential на выбранный узел. Повтор операции
   безопасен; чужие peers не изменяются. Публикация разрешена только после ready.
3. Issuer строит per-device schema2 с конкретными endpoints и credential. Envelope
   подписывается действующим доверенным ключом и адресно шифруется. Онлайн relay и
   telemetry не получают offline signing key. На первом rollout выдача остаётся
   операторской; автоматический балансировщик не может обойти signing boundary.
4. Клиент проверяет подпись, identity/WG binding, revision, предыдущий hash, lease,
   возможности транспорта. Затем snapshot → apply → проверка реального трафика →
   commit + ACK; при сбое — rollback с прежней identity и floors.
5. Освобождение адреса возможно после подтверждённого удаления peer/credential.
   Истёкший таймер сам по себе не доказывает очистку удалённого узла. Состояние
   retiring остаётся зарезервированным при недоступном сервере.

Текущий product reconciler знает WG/Docker и ограничивает изменения топологии;
Friends использует отдельные stores. Нельзя подключать новый allocator к одному
из них без сверки существующих выдач и миграционного плана. Пулы существующих
устройств не перенумеровываются при добавлении сервера.

## Добавление и вывод сервера

Добавление: зарегистрировать ID/domain/IP/pool в provisioning → установить runtime
и ключи на сервере → проверить firewall, внешний адрес, транспорт и health →
включить authenticated telemetry → перевести в active → зарезервировать тестовое
устройство → подготовить и проверить signed config → разрешить новые назначения.

Вывод: draining запрещает новые назначения, существующие leases сохраняются →
контролируемая миграция/истечение с подтверждённой очисткой → disabled. Смена
внешнего IP проходит через новую revision и период перекрытия, если старый адрес
ещё доступен. Клиенты получают endpoints в новой signed config; UI не зашивает IP.

## Совместимость существующих устройств

Friends и старый managed pilot — разные контуры. В Android `FriendsIdentityVault`
и `ControlIdentityVault` хранят разные identities; простой запуск sync-control
после Friends-регистрации не является интеграцией. Для Friends следует использовать
уже имеющуюся Friends identity и отдельный явно привязанный managed journal.
Автоматическая генерация новых ключей, копирование одного journal на другую identity
и сброс floor запрещены. Старый pilot journal сохраняется как отдельный namespace;
конкурирующие владельцы VPN должны проходить общий arbiter/recovery.

Linux должен связать Friends owner с managed runner и общим operation owner.
Windows — использовать существующую защищённую Friends identity per SID, добавить
durable journal/outbox и общую сериализацию broker/Auto/TCP. Существующий pipe имеет
лимит 16 KiB: envelope до 64 KiB не отправляется туда увеличением legacy limits.
Предпочтителен broker-owned bounded intake с явной авторизацией SID.

AWG3.1 в обычном Friends VPN уже есть. С [checkpoint5.3а](releases/2026-09-24-managed-awg31.ru.md)
managed schema2/issuer и Python verifier поддерживают его с явным capability opt-in;
native managed клиенты и Linux runner ещё не включены. Общий новый corpus подготовлен,
его native conformance и runtime acceptance трёх платформ ещё нужны.
Прежний immutable corpus не перегенерируется ради сокрытия изменения семантики.

## Обязательная приёмка

| ID | Сценарий и наблюдаемый результат |
| --- | --- |
| S5-01 | Основной API недоступен тестовому клиенту, VPN отсутствует: независимый ingress доставляет envelope, native verifier принимает его, после traffic health появляется COMMITTED ACK |
| S5-02 | Повтор exact bytes не запускает apply; чужой адресат, неверная подпись, replay, expiry и несовместимая версия не меняют профиль |
| S5-03 | Crash на каждой durable границе, restart клиента/службы: rollback/recovery до новых операций, floors не уменьшаются |
| S5-04 | Потеря carrier и ответа ACK при рабочем VPN: VPN остаётся, outbox повторяет те же bytes, relay хранит ACK идемпотентно |
| S5-05 | Плохой endpoint/неуспешный traffic health: прежний рабочий профиль восстановлен; истёкший профиль не переподключается |
| S5-06 | Friends-устройство включено в managed без новой регистрации и смены ключей; ручные действия и фон не обходят owner |
| F-01 | Третий сервер, в том числе в уже существующей стране, доступен совместимым клиентам без новой сборки |
| F-02 | Параллельные выдачи/повторы/падение reconciler не дублируют IP, не превышают ёмкость и не публикуют неготового peer |
| F-03 | Stale/поддельные/чужой revision метрики, полный узел, неверный transport/family: новых назначений нет |
| F-04 | Добавление узла и draining не перемещают здоровые действующие подключения; новые распределяются с учётом веса и запаса |
| F-05 | Смена внешнего IP доставлена через signed revision; старые floors/leases сохранены, откат не требует восстановления старой DB |
| F-06 | Недоступный удаляемый сервер не освобождает адреса до подтверждения очистки; bootstrap rotation сохраняет рабочий вход |

S5-01–06 выполняются на Android/Linux/native Windows с exact builds и evidence.
Блокировки и crash вводятся только для изолированного тестового устройства/процесса,
не остановкой общего API для всех пользователей. F-01 не требует покупки VPS:
функциональные проверки допускают изолированный дополнительный gateway, но это не
подменяет сетевую приёмку реального нового хоста. Unit tests не закрывают эти live gates.
